## 1. 프로젝트 개요

| 항목 | 내용 |
| --- | --- |
| 프로젝트명 | 성취기준 연계 에듀테크 교수학습과정안·활동지 자동 생성 시스템 |
| 요구사항 ID | REQ-005 |
| 요구사항명 | 검증·오케스트레이션 |
| 담당 파일 | `app/agents/validate/`, `app/agents/orchestrate.py` |
| 담당자 | 김준명 (D) |
| 작성일 | 2026-08-02 (최종 수정 2026-08-03) |
| 문서 버전 | v1.3 |

본 문서는 A1·A2·B·C(정보수집·검색·매핑·교안생성)가 산출한 교안 초안을 기반으로, 학년 누적 제약조건을 검증하고 실패 시 재생성을 요청하는 피드백 루프를 정의하며, 전체 에이전트 파이프라인을 순서대로 호출하는 오케스트레이션에 대한 요구사항을 정의한다. 인프라·웹 인터페이스 셸은 REQ-006(E) 문서에서 별도로 다룬다.

**핵심 설계 원칙**

- 검증 기준 명시화: "느낌"이 아닌 정량적(금지 용어 리스트) + 규칙 기반 논리 체크의 2단계 기준으로 판단한다.
- 무한 루프 방지: 검증 실패 시 재생성은 최대 N회로 제한하고, 초과 시 최선안 + 경고 표시로 강제 종료한다.
- 관심사 분리: 판단 로직(검증)과 흐름 제어(오케스트레이션)를 분리하여, 오케스트레이션은 결정론적으로 고정하고 각 에이전트의 판단만 자율적으로 동작하게 한다.
- 파일 소유 경계: D는 `agents/validate/`, `agents/orchestrate.py`만 소유하며, 공통 인프라(`lib/`, `main.py`, 배포)는 E(REQ-006)가 소유한다.
- 하류 소비자 기준 스키마 통일: `ValidationResult`는 이를 소비하는 C(REQ-004)가 기대하는 필드명·타입을 그대로 따른다. 별도 변환 계층을 두지 않아 오케스트레이터의 책임을 최소화한다.
- **전역 컨텍스트와 단계별 산출물의 분리(v1.2 추가)**: `target_grade`처럼 여러 단계가 동시에 필요로 하는 값은 특정 에이전트의 출력 스키마에 끼워넣지 않는다. 대신 오케스트레이터가 `PipelineContext`로 명시적으로 관리하며, 필요한 함수는 이를 별도 인자로 받는다. 반면 `inquiry_activities`처럼 특정 단계(A2)의 산출물에 종속된 부속 데이터는 그 값을 실제로 선택한 에이전트(B)의 출력에 패스스루로 포함시킨다.

**하위 기능 구성**

- VALID-000: 데이터 모델
- VALID-001: 학년 제약조건 검증
- ORCH-001: 파이프라인 오케스트레이션
- ORCH-002: 재시도 및 종료조건

### 0. 데이터 모델 정의 (VALID-000)

검증·오케스트레이션 파이프라인 전체에서 공유되는 데이터 타입을 정의한다. 각 모델은 Python Pydantic 모델로 구현되며, `app/lib/types.py`(1일차 전원 합의) 기준을 따른다.

#### VALID-000-1. ValidationResult

검증 1회 실행 결과를 표현하는 데이터 클래스. `agents/validate/logic.py`가 생성하고, `agents/orchestrate.py`가 수집하여 재시도 여부를 판단한다. 필드명·타입은 C(REQ-004, LG-004)가 기대하는 입력 형식을 그대로 따른다.

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| passed | bool | 학년 제약조건 통과 여부 (True: 통과, False: 위반) |
| violations | list[str] | 학년 누적 범위를 벗어난 용어 목록 |
| retry_feedback | str | 위반 사유 설명, C 재호출 시 프롬프트에 그대로 재사용 |

**참고**: "재시도 횟수 초과" 여부는 `ValidationResult`가 아니라 오케스트레이터가 자체적으로 관리하는 카운터로 판단한다(ORCH-002 참고). `validate()`는 매 호출마다 해당 교안의 통과 여부만 판단하며, 몇 번째 시도인지는 알 필요가 없다.

#### VALID-000-2. PipelineContext (v1.2 신규)

파이프라인 전체에 걸쳐 여러 단계가 공통으로 필요로 하는 전역 입력값을 담는 객체. `agents/orchestrate.py`가 사용자 최초 입력을 받는 시점에 1회 생성하여, 이를 필요로 하는 각 에이전트 함수에 명시적 인자로 전달한다. 특정 에이전트의 판단 결과가 아니므로 어떤 단계의 출력 스키마에도 포함시키지 않는다.

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| target_grade | int | 대상 학년(1~6). A1·A2는 자체 입력 스키마(ConceptInput, SearchQuery)로 이미 받고 있으나, C(LessonInput)는 이 경로로 전달받는다 |
| subject_hint | Subject | None | 과목 힌트(선택). 필요 시 하위 단계에서 참조 |

**설계 근거**: `target_grade`는 A1·A2·D·C가 모두 필요로 하지만 어느 하나가 "생성"하는 값이 아니라 사용자가 최초에 입력한 값을 그대로 나르는 것뿐이다. 이를 B(REQ-003)의 `MappingResult`처럼 특정 단계의 출력 스키마에 끼워넣으면, 그 단계가 자기 책임이 아닌 필드까지 짊어지게 되고 이후 또 다른 전역값이 필요해질 때마다 여러 단계의 출력 스키마를 연쇄적으로 수정해야 한다. `PipelineContext`로 분리하면 전역값 추가는 이 스키마 한 곳만 수정하면 된다.

#### VALID-000-3. ValidationResult 외 패스스루 데이터에 대한 참고

`inquiry_activities`(A2의 `CurriculumChunk` 필드)는 B가 선택한 청크에 종속된 데이터이므로 `PipelineContext`로 다루지 않는다. B(REQ-003)가 자신의 출력(`MappingResult`)에 그대로 실어 C에 전달하는 방식으로 별도 확정되었으며, 본 문서의 관리 범위 밖이다.

#### VALID-000-4. PipelineResult

전체 파이프라인 실행 결과를 표현하는 최종 반환 데이터 클래스. `agents/orchestrate.py`가 생성하여 `main.py`(E 소유)의 라우트로 전달한다.

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| lesson_plan | dict | 최종 교안·활동지 내용 |
| validation | ValidationResult | 최종 검증 결과 (VALID-000-1 스키마) |
| warning | str | None | 재시도 초과로 강제 반환된 경우의 경고 문구 |

### 1. 학년 제약조건 검증 (VALID-001)

생성된 교안에 대상 학년까지 누적으로 배우지 않은 용어, 또는 초등 학습자에게 그대로 노출되면 안 되는 AI 전문 용어가 포함되어 있는지 확인한다.

| 항목 | 내용 | 핵심 포인트 | 비고 |
| --- | --- | --- | --- |
| 입력 | 교안 텍스트(C 출력), 대상 학년(`PipelineContext.target_grade`), 과목(`MappingResult.subject`), **`caution_terms`(A1 `StructuredConcept`, 오케스트레이터가 전달)** | 두 종류의 금지 용어를 함께 사용 | 과목은 B가 청크를 선택한 시점에 확정된 값을 사용(`PipelineContext.subject_hint`는 Optional이라 검증 기준으로 부적합) |
| 처리 | 1단계: **금지 용어 합집합 체크**(정량적, 자동화) — ① 학년별 금지 용어 리스트(과목·학년 기준, `curriculum_chunks` 파생) ∪ ② A1의 `caution_terms`(개념별 동적). 2단계: 최소 논리 체크리스트(비유-개념 대응 관계 검증, 규칙 기반+LLM 판단 병행) | 두 리스트는 판단 축이 다름 — ①은 **학년 초과**, ②는 **독자 부적합**. 별도 관리하되 검증 시점에 합집합으로 적용 | 1단계 우선 구현, 2단계는 시간 여유 시 |
| 출력 | ValidationResult | VALID-000-1 스키마 | ORCH-002로 전달 |
| 예외 처리 | 금지 용어 리스트에 없는 신규 용어 등장 시 통과 처리(오탐 방지). **`caution_terms`는 LLM 생성값이라 일상어("특징", "기준", "규칙")가 섞일 수 있으므로 어절 경계 기준 완전 일치로만 매칭하고, 1~2음절 단독 항목은 검증에서 제외** | 과도한 차단 방지 | 부분 문자열 매칭 금지("동물의 특징" 같은 정상 표현이 위반으로 잡힘) |

### 2. 파이프라인 오케스트레이션 (ORCH-001)

사용자 입력을 받으면 `PipelineContext`를 먼저 생성하고, A1(정보수집) → A2(검색) → B(매핑) → C(교안생성) → VALID-001(검증) 순으로 에이전트를 호출하며, 각 단계의 출력과 `PipelineContext`를 필요한 다음 단계에 전달한다.

| 항목 | 내용 | 핵심 포인트 | 비고 |
| --- | --- | --- | --- |
| 입력 | AI 개념, 대상 학년 (사용자 입력) | 성취기준은 입력값에서 제외, A1·A2가 검색으로 채움 | 정방향 기준. 역방향(단원→개념)은 별도 계약 |
| 처리 | ① 사용자 입력으로 `PipelineContext` 생성(VALID-000-2) ② A1 호출. **`status`가 `success`가 아니면(`unsupported_concept`/`ambiguous_input`) 이후 단계를 호출하지 않고 즉시 종료** ③ A2·B를 순차 호출. **B 호출 시 `PipelineContext`를 함께 전달**(B-02 평가 기준 중 학생 이해도·비유 가능성이 학년 의존적) ④ C 호출 시 B의 `MappingResult`(`inquiry_activities` 패스스루 포함)와 `PipelineContext`(`target_grade`)를 함께 전달 ⑤ VALID-001로 검증. **이때 ②에서 받은 `ConceptCollectResult.concept.caution_terms`와 `MappingResult.subject`를 함께 전달** | 오케스트레이터는 결정론적 흐름만 담당, 판단은 각 에이전트에 위임. **A1 산출물은 다음 단계 입력으로 쓰인 뒤에도 검증 단계까지 지역 변수로 보관한다**(VALID-001이 `caution_terms`를 필요로 함) | Deterministic Shell, Probabilistic Core 원칙 |
| 출력 | PipelineResult | VALID-000-4 스키마 | `main.py`(E) 라우트로 전달 |
| 예외 처리 | 특정 에이전트 호출 실패(API 오류 등) 시 공통 에러 핸들러로 처리, 사용자에게 재시도 안내. **A1의 `unsupported_concept`/`ambiguous_input`은 오류가 아닌 정상 종료로 취급하되, 사용자 노출 문구는 E와 협의**(A1이 유사 개념 임의 대체를 금지하므로 파이프라인도 임의 진행하지 않음) | 파이프라인 전체가 중단되지 않도록 방어 | `lib/gemini.py`(E 소유) 공통 재시도 로직과 연계 |

### 3. 재시도 및 종료조건 (ORCH-002)

검증 실패 시 교안 재생성을 요청하되, 무한 루프를 방지하기 위한 명확한 종료조건을 둔다. `ValidationResult`가 이미 C(REQ-004, LG-004)가 기대하는 형태(`passed`/`violations`/`retry_feedback`)를 그대로 따르므로, 오케스트레이터는 변환 없이 이 값을 바로 C에 전달한다. 재시도 횟수는 오케스트레이터가 반복문 안에서 로컬 변수로 직접 관리한다.

| 항목 | 내용 | 핵심 포인트 | 비고 |
| --- | --- | --- | --- |
| 입력 | ValidationResult (passed=False) | 최대 재시도 횟수 상수로 관리(오케스트레이터 로컬 변수) | 기본값 3회 |
| 처리 | ① `passed=False`면 `ValidationResult`를 변환 없이 그대로 C 재호출 입력으로 전달(이때 `PipelineContext`도 함께 재전달) ② 오케스트레이터가 유지하는 재시도 카운터를 1 증가 ③ C의 재생성 결과를 다시 `validate()`로 재검증 | 별도 변환 계층 없이 D→C가 직결됨 | 재시도 카운터는 `ValidationResult`가 아닌 `agents/orchestrate.py`의 반복문 지역 변수로 관리 |
| 출력 | passed=True 시 정상 반환, 카운터가 최대치를 초과하면 마지막 결과 + 경고 문구로 강제 반환 | 최대 재시도 횟수 초과해도 사용자에게 결과는 항상 반환 | 데모 중 무응답 방지. 이 판단은 오케스트레이터 로직이며 D 스키마에는 별도 상태값을 두지 않는다 |
| 예외 처리 | 재시도 중 API 실패 발생 시 즉시 중단, 마지막 성공 결과로 폴백 | 재시도가 오히려 장애를 키우지 않도록 방어 | - |
