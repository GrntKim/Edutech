## 1. 프로젝트 개요

| 항목 | 내용 |

| 프로젝트명 | 성취기준 연계 에듀테크 교수학습과정안·활동지 자동 생성 시스템 |
| 요구사항 ID | REQ-002 |
| 요구사항명 | 교육과정 검색 엔진 (RAG Retrieval) |
| 담당 파일 | `app/scripts/ingest_curriculum.py`, `app/agents/curriculum_search/`(`__init__.py`/`logic.py`/`prompts.py`/`schema.py`) |
| 담당자 | 박지민 (A2) |
| 작성일 | 2026-07-31 |
| 문서 버전 | v3.9 |

본 문서는 A1(개념 수집)이 생성한 **AI 개념의 구조화된 정의**를 입력받아, NCIC 2022 개정 교육과정(**(v3.3) 수학·과학·실과·미술**) 성취기준 문서를 대상으로 **대상 학년까지 누적으로 학습한 범위 안에서 의미적으로 관련된 단원 후보를 검색**하는 기능의 요구사항을 정의한다. 본 모듈의 출력은 B(매핑 에이전트)의 입력으로 사용된다.

**명칭에 대한 주석 (v3.0 갱신)**: 본 모듈은 팀 내 파일 컨벤션상 `app/agents/` 디렉토리에 위치한다. v2.0까지는 임베딩 유사도·메타데이터 필터링만 쓰는 결정론적 검색 알고리즘이라 "에이전트"가 아니라고 못박았으나, RS-005 골든셋 실측에서 순수 임베딩 검색의 개념 변별력이 부족함이 확인되어 v3.0부터는 **dense+sparse 하이브리드 검색으로 후보를 추리고, 최종 판단은 LLM(Gemini)이 재정렬·근거 생성까지 수행**하는 구조로 바뀌었다. 즉 이제 "Retrieval" 절반만이 아니라 "Augmented Generation"의 판단 요소도 일부 포함한다 — 완전한 결정론적 알고리즘이라는 이전 주장은 더 이상 정확하지 않다. 다만 여전히 최종 창작(교안 생성)을 수행하지 않고 후보 검색·근거 부여까지만 담당하므로, "검색 엔진" 명칭은 유지하되 "결정론적"이라는 수식은 제거한다.

**핵심 설계 원칙 (v3.0 갱신)**

> 1. ~~결정론적 검색~~ → **재현 가능한 검색 + LLM 최종 판단**: dense/sparse 후보 추리기(RRF 융합)까지는 동일 입력에 동일 결과를 재현하지만, 최종 재정렬은 LLM이 수행하므로 완전한 재현성은 보장하지 않는다. 근거(reasoning)를 함께 반환해 판단 과정을 추적 가능하게 한다.
> 2. 누적 범위 제약: 검색 대상은 항상 대상 학년까지 **누적으로 학습한 범위**로 한정한다(예: 4학년 입력 시 1~4학년 전체).
> 3. Recall 우선, Precision은 후단에 위임 → **v3.0에서 일부 수정**: 임베딩 검색만으로는 정답을 top-k 안에 포함시키는 것조차 어려움이 실측으로 확인되어, dense+sparse 융합으로 recall을 확보하고 정교한 의미 판단(precision)은 본 모듈 내 LLM 리랭킹 단계로 앞당겼다. B는 여전히 최종 매핑·활용을 담당한다.
> 4. 도메인 갭 대응: AI 개념 어휘와 초등 교육과정 어휘 사이의 표현 차이를 인지하고, A1의 쿼리 재작성 및 hybrid search로 완화한다.
> 5. 확장 가능한 구조: 과목을 하드코딩하지 않고 메타데이터 기반으로 설계하여, 2단계에서 과목 추가 시 로직 변경 없이 데이터만 추가되도록 한다.

| MATH | 수학 | 1단계 |
| SCIENCE | 과학 | 1단계 |

#### RS-000-2. GradeBand (열거형)

| 값 | 범위 |
| --- | --- |
| G1_2 | 1~2학년 |
| G3_4 | 3~4학년 |
| G5_6 | 5~6학년 |

**설계 근거**: 청크의 학년 태그를 개별 학년(1~6)이 아닌 학년군으로 둔 것은 NCIC 원문 자체가 2022 개정 교육과정에 따라 성취기준을 학년군 단위로 발행하기 때문이다(예: `[4수01-01]`은 "4학년"이 아니라 "3~4학년군" 전체에 적용). 원문에 학년별로 분리된 내용이 존재하지 않으므로, 청크 메타데이터를 개별 학년으로 세분화하면 존재하지 않는 구분을 인위적으로 만드는 것이 되어 오히려 부정확하다.

단, **사용자 입력(target_grade)은 개별 학년(1~6)을 그대로 받는다.** 검색 시 아래와 같이 개별 학년을 포함 학년군 집합으로 매핑한 뒤 필터링한다.

| target_grade 입력 | 포함되는 GradeBand |
| --- | --- |
| 1, 2 | {G1_2} |
| 3, 4 | {G1_2, G3_4} |
| 5, 6 | {G1_2, G3_4, G5_6} |

즉 target_grade=3과 target_grade=4는 동일한 검색 대상 풀을 갖는다 — 이는 버그가 아니라 원본 학년군제를 그대로 반영한 정확한 동작이다.

### 1. 문서 파싱 및 구조 보존 (RS-001)

**실제 원본 파일 형식 확인 결과(3차 수정, 확정)**: NCIC 별책8(수학과, 263p)·별책9(과학과, 292p) **모두 PDF 배포판을 확보하여 실측 검증 완료**. 두 과목 모두 PyMuPDF 단순 텍스트 추출만으로 성취기준 원문이 표 유실 없이 완전한 문장으로 추출됨을 확인했다. **HWP+`pyhwp` 경로는 더 이상 필요하지 않으며, 3단계(사회 등 확장) 시 해당 과목의 PDF 배포판을 우선 확인하고 없을 때만 예비 경로로 남겨둔다.** **(v3.3 추가)** 이후 실과(기술·가정)/정보과, 미술과 PDF도 동일 경로(PyMuPDF)로 확보·파싱 완료. **(v3.8 추가)** 사회과(별책7)·국어과(별책5) PDF도 동일 경로로 확보·파싱 완료 — 단, 사회과 PDF는 성취기준 코드 337개 중 2개(`4사01-01`/`4사01-02`)가 hyphen 대신 en-dash로 표기돼 있어 별도 정규화(`_normalize_code()`)가 필요했음(다른 5개 과목 PDF에는 이 문제 없음).

| 항목 | 내용 | 핵심 포인트 | 비고 |
| --- | --- | --- | --- |
| 입력 | NCIC 별책 PDF (수학과[별책8], 과학과[별책9], **(v3.3 추가)** 실과(기술·가정)/정보과, 미술과, **(v3.8 추가)** 사회과[별책7], 국어과[별책5] 확보·검증 완료) | 6과목 모두 PDF 경로로 통일 | 남은 2단계 확장 과목도 PDF 우선 탐색 |
| 처리 | PyMuPDF로 페이지 텍스트 순차 추출 → `[초등학교 X∼Y학년]`(학년군) / `(N) 영역명` / 내용요소 / `[코드] 성취기준 문장` / (과학만) `<탐구 활동>` / `(가) 성취기준 해설` / `(나) 적용 시 고려 사항` 계층을 정규식·순서 기반으로 파싱 | 성취기준 원문이 표가 아닌 일반 텍스트라 파싱 난이도 낮음 | 수학과는 내용요소 앞 불릿 기호가 폰트 인코딩 문제로 깨진 음절(예: `숔`)로 나오므로 해당 문자 스트립 처리 필요. 과학과는 해당 이슈 없음. **(v3.3 추가)** 실과는 학년군 범위 헤더(`[초등학교 X∼Y학년]`) 대신 `[초등학교 실과]`처럼 과목명만 표기되어 별도 헤더 패턴 처리 필요(실과는 5~6학년군에만 존재하므로 그 학년군으로 고정 매핑, `app/scripts/ingest_curriculum.py`의 `_SIMPLE_SCHOOL_HEADER_RE`) |
| 출력 | 구조화된 원문 텍스트(계층 태그 포함 JSON) | RS-002 입력으로 전달 | - |
| 예외 처리 | (미사용 예비 경로) 향후 PDF 미배포 과목 발생 시 HWP+`pyhwp`(`hwp5html`+BeautifulSoup 표 파싱) 적용 | 1단계 스코프에서는 발생하지 않음 | 샘플 20건 이상 수작업 대조 |

**부가 발견 사항**:
- 과학과 원문에는 성취기준 외에 `<탐구 활동>`(실제 수업 활동 예시)이 별도로 포함되어 있다 → CurriculumChunk에 `inquiry_activities: list[str]` 필드 추가 검토(C의 활동지 생성에 직접 활용 가능).
- "(나) 적용 시 고려 사항"에 학년군·교과 간 연계가 원문 텍스트로 이미 명시되어 있다(예: "초등학교 5∼6학년군 '물체의 운동'과 연계된다") → 별도 엔티티 추출 없이 정규식만으로 선수/연계 관계 그래프를 구성할 수 있어, 2단계 지식그래프 확장 시 데이터 구축 비용이 예상보다 낮아질 수 있음.

### 3. 임베딩 및 Cloud SQL(pgvector) 적재 (RS-003)

| 항목 | 내용 | 핵심 포인트 | 비고 |
| --- | --- | --- | --- |
| 입력 | CurriculumChunk 리스트 | - | - |
| 처리 | **(v3.4 확정)** `nlpai-lab/KoE5`로 최종 확정(`RS-006_검색구조_의사결정_기록.md` §9.18). §8.8에서는 당시 리랭커(정정 전) 기준으로 `ko-sroberta-multitask` 유지를 결정했으나, 리랭커를 `gemini-3.6-flash`로 정정한 뒤(§9.12) 4개 모델을 다시 end-to-end 비교하니 결론이 뒤집힘 — KoE5가 Recall 78.57%→83.33%로 가장 높음(재현 시 78.57~83.33% 사이 변동, 리랭커 비결정성 때문에 반복 시행 없이는 정확한 격차 확정 불가). KoE5는 query:/passage: 프리픽스가 필요해 `embed_text(text, *, is_query=False)`로 프리픽스 로직을 프로덕션 코드에 정식 이식(`app/agents/curriculum_search/logic.py`). OpenAI text-embedding-3는 로컬 무료 모델 우선 방침으로 미착수. 전체 청크 임베딩 후 `pgvector` 확장이 설치된 Cloud SQL(PostgreSQL) 인스턴스에 적재. **(v3.4 추가)** KoE5는 1024차원인데 `curriculum_chunks.embedding` 컬럼이 이전 모델(768차원) 기준으로 이미 생성돼 있었음 — 관리자가 `ALTER TABLE curriculum_chunks ALTER COLUMN embedding TYPE vector(1024)`로 1회 스키마 변경(적재 데이터 0건 시점이라 마이그레이션 이슈 없음). 또한 `app/scripts/ingest_curriculum.py`가 매 실행마다 `CREATE EXTENSION`/`CREATE TABLE` DDL을 직접 실행하고 있었는데, `app_user`는 DDL 권한이 없어 실제 Cloud SQL에서는 항상 실패하는 구조였음 — DDL 실행 코드를 제거하고(테이블/확장은 관리자가 이미 생성) raw `psycopg` 연결도 `app/lib/db.py`의 `get_connection()` 경유로 교체 | 인덱싱과 검색 시 동일 모델 강제 | 모델 버전 고정, 변경 시 전체 재적재. **(v3.3)** dense-only 벤치마크만으로 모델을 바꾸면 안 되고 end-to-end 실측이 필수라는 원칙이 §8.8에서 확립됨. **(v3.4)** 그 원칙을 리랭커 정정 후 재적용해 결론 자체가 다시 뒤집힘 — 리랭커가 바뀌면 임베딩 모델 순위도 재검증 대상이라는 교훈 추가. 임베딩 모델(차원)을 바꿀 때는 DB 스키마도 함께 재검증 대상이라는 교훈도 추가 |
| 출력 | Cloud SQL `curriculum_chunks` 테이블(임베딩 포함) | 팀 공용 GCP 프로젝트 내 인스턴스 사용 | `lib/db.py`(D)의 연결 설정 사용. **(v3.4)** 테이블명 `curriculum_chunks` 확정(성취기준 코드 1개 = 청크 1개라 "chunks"가 정확한 명칭) — `app/agents/curriculum_search/logic.py`의 `_FETCH_BAND_SQL` 실제 사용 테이블명과 동일. `embedding` 컬럼은 `VECTOR(1024)`(KoE5 기준, v3.4 스키마 변경 반영) |
| 예외 처리 | 적재 실패 시 청크 단위 재시도, 중복 chunk_id 방지(UPSERT) | 배치 스크립트 안정성 | 로컬 1회 실행이므로 idempotent하게 설계 |

### 4. Hybrid 검색 API (RS-004)

**v3.0 전면 개정**: v2.0까지는 순수 벡터 kNN(임베딩 코사인 거리 top-k)만 수행하고 "LLM 호출 없음"이 원칙이었다. RS-005 골든셋 실측 결과, 서로 다른 AI 개념(예: "분류"/"패턴 인식"/"군집화")에 대해 top-5 후보와 유사도 점수가 거의 동일하게 나오는 등 임베딩 단독으로는 개념적 변별력이 부족함이 확인되어(상세 근거·검토한 대안: `RS-006_검색구조_의사결정_기록.md`), 아래와 같이 dense+sparse 하이브리드 검색 + LLM 리랭킹 구조로 변경한다.

| 항목 | 내용 | 핵심 포인트 | 비고 |
| --- | --- | --- | --- |
| 입력 | SearchQuery (concept_name, concept_definition, target_grade, top_k) | A1의 쿼리 재작성 결과 사용 | v3.0부터 concept_name도 sparse 검색·프롬프트에 함께 사용 |
| 처리 | ① target_grade 이하 GradeBand로 SQL `WHERE` 필터 (LIMIT 없이 전량 조회, **(v3.8) 최대 424개** — 사회·국어 추가로 288개에서 증가, v3.3 시점엔 223개) → ② concept_definition을 RS-003과 동일 모델로 임베딩해 전량에 대해 dense 코사인 유사도 계산(Python/NumPy) → ③ concept_name+concept_definition을 음절 bigram으로 토크나이즈해 BM25(sparse) 점수 계산(형태소 분석기 미사용) → ④ dense/sparse 순위를 RRF(Reciprocal Rank Fusion)로 융합 후 **(v3.3 추가)** 질의의 target_grade가 속한 학년군과 청크 자신의 grade_band 사이 거리(0/1/2단계)에 따른 가중치(1.0/0.8/0.6)를 곱해 재정렬 → 상위 `CANDIDATE_POOL_SIZE`(20)개 후보 선정 → ⑤ 후보를 `app/lib/gemini.py`의 `generate_structured()` 경유로 Gemini(`gemini-3.6-flash`, `thinking_level="low"`)에 구조화 출력(JSON) 프롬프트로 전달해 관련성 순 재정렬 + 선택 근거(reasoning) 생성, 관련 후보가 없으면 빈 리스트 반환 | 메타데이터 필터 + dense/sparse 융합 + 학년 거리 가중치 + LLM 최종 판단 | **"LLM 호출 없음" 전제 폐기.** 후보 풀을 20개로 제한하는 이유: 청크 평균 900자 기준 전량(424개)을 매 질의 LLM에 넣으면 입력 토큰이 10만 개 이상으로 NFR-002-1을 위반함. 모델은 alias(`-latest`)가 아니라 버전 고정 문자열 사용(NFR-001-6 재현성) — `google.genai` 직접 호출은 팀 규약상 금지, 전 에이전트 공용 래퍼 경유. **(v3.3)** ④의 학년 거리 가중치는 `GRADE_TO_BANDS`가 누적 구조라 target_grade 5~6 질의는 필터링 효과가 거의 없어(코퍼스 전체가 무차별 후보가 됨) 추가됨 — 골든셋 42행 스윕 실측으로 가중치 값 확정(상세: `RS-006_검색구조_의사결정_기록.md` §9.7~9.8) |
| 출력 | SearchResult 리스트 (reasoning 필드 포함) | B의 입력 스키마와 사전 합의 필수 | RS-000-5 참고. reasoning은 optional이라 기존 소비자와 호환 |
| 예외 처리 | 필터링 후 후보 0건 시 학년 범위를 임의로 완화하지 않고 빈 리스트 반환. LLM이 진짜 관련 후보가 없다고 판단한 경우도 동일하게 빈 리스트 반환(억지로 채우지 않음) | 임의 확장 금지, B/D에 명확히 전달 | Cloud SQL 연결 실패·LLM 호출 실패 시 `CurriculumSearchError`로 명확한 에러 반환 |
