## 1. 심각 — 코드 작성 전 반드시 합의 필요

### 1-1. B가 가정한 A1 출력 스키마가 A1의 실제 스키마와 다름
B(REQ003) 2장은 A1 입력을 아래 필드로 명시:
`concept_name, concept_definition, core_principles, key_features, education_query`

A1(REQ001) RS-000-3 `StructuredConcept`의 실제 필드:
`concept_name, category, one_line_definition, core_mechanism, key_operations, prerequisite_ideas, everyday_examples, caution_terms`

`concept_name`을 제외한 나머지 4개 필드명이 전부 다름(단순 오탈자 수준이 아니라 필드 구성 자체가 다름). B가 이 스키마 그대로 프롬프트/파서를 짜면 A1 구현체와 바로 깨진다. B와 A1이 동일 문서(A1의 RS-000-3)를 기준으로 재정렬해야 함.

### 1-2. B 출력 → C 입력 필드명 불일치
- B(REQ003) 출력 `MappingResult.analogy`
- C(REQ004) 입력 `LessonInput.analogy_text`

이름만 다르고 의미는 같아 보이지만, 계약 문서상으로는 다른 필드다. 오케스트레이터(D)가 임의로 매핑해줄 것으로 기대하면 안 되고, B/C 둘 중 하나로 통일 필요.

### 1-3. `target_grade`, `inquiry_activities`가 C에 도달하는 경로가 문서화되어 있지 않음
C(REQ004)의 `LessonInput`은 `target_grade`와 `inquiry_activities`를 요구한다. 그런데:
- `target_grade`는 사용자 최초 입력(A1의 `ConceptInput`)에만 존재하고, A2의 `SearchResult`에도 B의 `MappingResult`에도 없다.
- `inquiry_activities`는 A2의 `CurriculumChunk` 필드지만, B(REQ003) 입력 필드 목록에는 빠져 있고 B의 `MappingResult` 출력에도 없다.

즉 파이프라인 스키마 체인(A1→A2→B→C)만 따라가면 두 값 다 C에 도달할 방법이 없다. D(REQ005 v1.2)의 ORCH-001은 여전히 "이전 단계 출력을 다음 단계 입력으로 매핑"이라고만 되어 있어(오늘 분리 작업에서도 그대로 유지됨), "원본 사용자 입력을 각 단계에 함께 실어 나른다"는 책임이 명시돼 있지 않다. 오케스트레이터가 매 단계 컨텍스트를 누적 전달하는 방식을 D가 명문화하거나, A2/B가 필드를 그대로 통과시키도록 스키마를 수정해야 한다. **REQ005/REQ006 분리와 무관하게 아직 미해결.**

### 1-4. 재시도 최대 횟수 불일치 — **[결정 완료, 2026-08-03] 3회로 통일**
- D(REQ005 v1.2) ORCH-002 / NFR-003-2: 최대 재시도 **2회** (기본값) → v1.3에서 **3회**로 수정 완료
- C(REQ004) LG-004: **"max_retries: 3 기준 준수"** (변경 없음, 원래부터 3)

팀 채널 합의로 D를 C의 숫자(3회)에 맞춤. REQ005 v1.3 반영 완료.

### 1-5. REQ 문서 파일명과 문서 내부 "요구사항 ID"가 서로 다른 넘버링 체계를 쓰고 있음 (분리 후 새 충돌 포함)
- D(REQ005) 1장 표: `요구사항 ID: REQ-003` — REQ-003은 이미 B(매핑)가 사실상 쓰는 자리(B 문서엔 ID 필드 자체가 없지만 파일명이 REQ003)라 겹친다. 원래 있던 이슈, 오늘 REQ006 분리 작업으로도 정정되지 않음.
- **[신규]** E(REQ006, 오늘 분리) 1장 표: `요구사항 ID: REQ-004` — REQ-004는 이미 C(교안생성, REQ004 v4.0)가 명시적으로 쓰고 있는 ID다("v4.0: 요구사항 ID REQ-003 → REQ-004로 변경"). REQ006 문서를 REQ005에서 그대로 잘라내면서 원본에 있던 "요구사항 ID: REQ-004" 표기를 정정하지 않아 C와 정면으로 충돌한다.
- 정리하면 파일명 기준(REQ001~006, A1~E)과 문서 내부 ID 필드가 전부 따로 논다. **전체 통일안 제안**: 파일명 순서를 그대로 요구사항 ID로 채택 — REQ-001(A1), REQ-002(A2), REQ-003(B), REQ-004(C), REQ-005(D 검증), REQ-006(E 인프라). D·E 문서의 표 값만 고치면 됨.

### 1-6. **[신규]** NFR ID도 REQ004(C)와 REQ006(E)이 동일하게 충돌
- C(REQ004, v4.1): `NFR-004-1`(파이프라인 60초, v4.1에서 2-3 해결과 함께 수정), `NFR-004-2`(피드백 반영 정확도), `NFR-004-3`(현장 가독성)
- E(REQ006, 오늘 분리): `NFR-004-1`(배포 가용성), `NFR-004-2`(요청 타임아웃), `NFR-004-3`(도메인 SSL 발급)

두 문서가 같은 ID로 완전히 다른 항목을 가리킨다. 1-5의 ID 정정안을 따르면 E의 NFR도 `NFR-006-x`로 재넘버링해야 함.

## 2. 중간 — 지금 고치면 저비용, 방치 시 통합 단계에서 재작업 유발

### 2-1. D의 검증 결과 스키마와 C가 서술하는 형태가 다름
- D(REQ005) `ValidationResult`: `status(PASS/FAIL/FAIL_MAX_RETRY), violated_terms, reason, retry_count`
- C(REQ004) LG-004 서술: "D 에이전트가 검증 과정에서 **passed: false** 판정을 내리며 전달한 **retry_feedback**(violations 내용)"

C는 boolean `passed` 필드와 `retry_feedback`/`violations`라는 이름을 언급하지만 D의 실제 스키마엔 그런 필드가 없다(`status`는 3-value enum, `violated_terms`가 가장 가까운 대응). 오케스트레이터가 `ValidationResult`를 C가 기대하는 형태로 변환해줘야 하는데 그 변환 로직이 어느 문서에도 없다.

### 2-2. `lib/` 소유권 — 문서는 정리됐지만 README가 못 따라감
- README.md 담당 역할표(158~164행): D 한 줄에 "검증, 오케스트레이션, 인프라"를 전부 묶어서 `lib/`, 배포 전반까지 D 소유로 기재. **E라는 행 자체가 없음.**
- D(REQ005 v1.2)는 오늘 분리로 "공통 인프라·서비스 골격(`main.py`, `lib/`, `static/`, `templates/`, 배포)은 E(REQ006)가 소유"라고 명확히 함.
- E(REQ006)도 "E는 `main.py`, `lib/`, `static/`, `templates/`, 배포 파이프라인을 소유"라고 동일하게 명시.

D/E 문서끼리는 이제 일치하지만, **README가 갱신되지 않아** 다른 팀원이 README만 보면 여전히 "lib 수정 시 D"로 알게 됨. REQ 문서 기준(D=검증만, E=인프라)으로 README 역할표에 E 행을 추가하거나, 실제로는 한 사람이 겸임하니 D 행에 "(D: 검증 / E: 인프라, 담당자 동일)"로 병기 필요.

### 2-3. 전체 파이프라인 지연 목표 충돌 가능성 — **[결정 완료, 2026-08-03] 60초로 통일**
- C(REQ004) NFR-004-1: ~~"D 검증 및 재귀 루프 포함 15~20초 이내 최종 산출"~~ → v4.1에서 **60초 이내**로 수정 완료
- D(REQ005) NFR-003-1: "파이프라인 전체 응답 지연: 재시도 포함 **60초 이내**" (변경 없음)

애초 이 검토에서 지적했던 대로 A1(10~15초)+A2(2초, 리랭킹 시 불확실)+B(p95 5초)만 합쳐도 최소 12~17초라 15~20초 목표는 낙관적이었음. D의 60초 기준으로 통일해 여유를 확보. C REQ004 v4.1 반영 완료.

### 2-4. B 문서의 포맷이 다른 문서와 다름
B(REQ003)에는 다른 문서에 있는 "개정 이력(Revision History)", "승인" 섹션이 없고 버전 번호도 없다. A2가 v3.0에서 검색 구조를 임베딩 단독 → dense+sparse+LLM 리랭킹으로 전면 변경했는데(reasoning 필드 추가 포함), B 문서가 이 변경을 반영해서 작성된 것인지 이전 버전 기준인지 문서만으로는 확인이 안 된다. 실제로 B가 인용하는 A2 SearchResult 필드 목록에는 `reasoning`이 빠져 있어, v2.0 이하 시점 기준으로 작성됐을 가능성이 있다.

### 2-5. 골든셋 소스 불일치 — **[결정 완료, 2026-08-03] 통일하지 않고 각자 사용**
- A1: "A2 골든셋을 공유(이중 라벨링 방지)"라고 명시
- A2: 골든셋을 `curriculum-search-engine/RS-005_골든셋_초안.csv`로 관리
- B: `tests/fixtures/golden_set.json` (JSON, 경로도 다름)을 언급하며 "골든셋 정확도 80% 이상"을 목표로 제시

팀 결정: A1/A2/B가 각자 자기 골든셋을 따로 관리해도 무방함(경로·포맷 강제 통일 불필요). 단, "80% 정확도" 같은 수치를 비교할 때는 서로 다른 데이터셋 기준이라는 점을 감안해야 함 — 동일 기준 비교가 필요해지면 그때 다시 논의. A1 문서의 "A2 골든셋을 공유"라는 서술만 실제로 공유할지 A1이 재확인해서 문구를 정리하면 됨(B는 무관).

### 2-6. B 문서의 파일 구조가 실제 레포 구조와 다름
B(REQ003) 6장 "담당 파일" 트리는 `project/agents/mapping.py`, `project/config/`, `project/tests/fixtures/` 형태(최상위 `project/` 기준, `mapping.py` 단일 파일)로 되어 있다. 실제 레포는 `app/agents/mapping/`(logic.py/prompts.py/schema.py/`__init__.py`로 구성된 패키지)이고 최상위 폴더명도 `project`가 아니다. `config/`, `tests/fixtures/`도 현재 레포에 존재하지 않는 새 최상위 폴더라 다른 팀원과 사전 합의가 필요하다.
