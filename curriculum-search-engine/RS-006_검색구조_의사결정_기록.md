# RS-006 검색 구조 의사결정 기록

`agents/curriculum_search`의 검색 방식을 순수 임베딩 유사도에서 하이브리드 검색 + LLM 리랭커로 바꾸기까지의 논의와 근거를 기록한다. 포트폴리오 작성 시 "왜 이 구조를 선택했는지"를 설명하는 용도.

## 1. 문제 발견 (2026-08-02)

RS-005 골든셋 초안(`RS-005_골든셋_초안.csv`)으로 실제 검색 결과를 검수하던 중, 순수 임베딩(`ko-sroberta-multitask` + 코사인 유사도) 검색이 잘 안 맞는다는 게 드러남.

- 유사도 점수가 질의 관련성과 무관하게 0.5~0.7 사이에 뭉쳐 있어 변별력이 거의 없음.
- "분류" / "패턴 인식" / "군집화"처럼 서로 다른 AI 개념인데 top-5 후보와 점수가 거의 동일하게 나옴 (임베딩이 개념을 구분 못 함).
- 실제 검수(박지민, 나윤서)에서도 후보 대부분을 "정답 아님"으로 판단, 상당수 행이 "없음"으로 처리됨.

## 2. 근본 원인

1. **모델-태스크 불일치**: `ko-sroberta-multitask`는 STS(문장 유사도)용 범용 모델이라, "AI 개념 정의(추상)" ↔ "초등 교육과정 성취기준(구체)" 사이의 개념적 도약을 잡아내는 리트리벌 태스크에는 최적화되어 있지 않음.
2. **"hybrid_search"라는 이름과 다르게 실제로는 순수 벡터 kNN**: `logic.py`의 `hybrid_search`는 키워드/BM25 등 sparse 신호 없이 pgvector 코사인 거리만으로 정렬함.
3. **코퍼스 규모 대비 과도한 top-k 절단**: `GRADE_TO_BANDS`(schema.py)가 누적 구조라서 target_grade 5~6 질의는 grade_band 필터링 결과가 전체 코퍼스(223개 중 223개)와 동일함. 이 상태에서 top_k=15~25로 자르면 정답이 애초에 후보에 안 들어가는 경우가 다수 발생.
   - 코퍼스 분포: 총 223개 (G1_2 29 / G3_4 98 / G5_6 96, MATH 121 / SCIENCE 102)

## 3. 검토한 대안

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| 순수 LLM (임베딩 제거, grade_band로만 필터링 후 전량을 LLM에 전달) | 정보 손실 없음, 구조 단순 | 코퍼스가 커지면 확장성 문제; 담당자가 임베딩 모델을 다뤄볼 학습 기회를 잃음 |
| 임베딩 top-k 확대(20~25) + LLM 리랭커 | 구현 간단 | 여전히 grade 5~6 질의에선 필터링 효과가 미미해 근본 해결 아님 |
| **dense+sparse 진짜 하이브리드(RRF) + LLM 최종 판단 (채택)** | 정확도 개선 + 임베딩 모델 실사용 경험 유지 + "hybrid_search"라는 이름에 부합 | 구현 범위가 가장 넓음 |

## 4. 결정

- **Dense**: 기존 `ko-sroberta-multitask` 임베딩 + 코사인 유사도는 그대로 유지.
- **Sparse**: 키워드/tsvector 기반 검색을 추가.
- 두 결과를 **RRF(Reciprocal Rank Fusion)**로 합쳐 후보 리스트 생성 (top_k는 코퍼스 규모 대비 넉넉하게 설정해 정답 누락 방지).
- 합쳐진 후보를 **Gemini 2.5 Flash**에 전달해 최종 재정렬 + 근거(또는 "없음") 반환.
- 임베딩을 완전히 걷어내지 않은 이유: 기술적으로는 이 코퍼스 크기(223개)에서 LLM-only가 더 간단하고 정확할 수 있지만, 담당자가 AI 엔지니어 지망생으로서 임베딩 모델을 실제로 의미 있게 써보는 경험 자체가 목적 중 하나였음. 그래서 "장식"이 아니라 실제로 기여하는 dense 신호로 남기는 방향을 택함.

## 5. 골든셋(RS-005) 라벨링 프로세스 관련 결정

- 팀원에게 보여주는 후보 개수는 인지 부하 때문에 5개로 유지 (20개로 늘리는 안은 기각).
- "없음" + 비고(정성적 재정의, 부분적 chunk_id 추정 등)가 달린 행은, 팀원에게 후보를 더 보여주는 대신 비고 텍스트를 근거로 전체 223개 코퍼스에서 재검색해 실제 정답을 채워 넣는 방식으로 보완.
- 완성된 골든셋으로 **Recall@k를 하이브리드+LLM 구조 적용 전/후로 비교**해 실제 개선 여부를 정량 검증할 예정 (아직 미실행).

## 6. 구현 결과 (2026-08-03)

- **후보 풀 크기 확정 근거**: 청크 텍스트(`unit_name+core_idea+achievement_text+explanation`) 평균 길이가 약 900자. grade_band 필터만 거친 후보를 전량(최대 223개) 그대로 LLM에 넘기면 입력 토큰이 약 10만 개 수준까지 올라가 NFR-002-1(2초 이내 응답)을 확실히 위반함. 따라서 RRF 융합 결과 상위 `CANDIDATE_POOL_SIZE = 20`개만 LLM에 전달하는 것으로 확정 (`agents/curriculum_search/logic.py`).
- **모델명 이슈**: `gemini-2.5-flash`는 신규 발급 API 키에는 404로 차단됨("no longer available to new users"). `genai.list_models()`로 확인한 결과 `gemini-flash-latest` alias는 정상 동작하고, 향후 모델 세대가 바뀌어도 계속 최신 flash 모델을 가리키므로 이걸로 확정. 실제 테스트(도형 분류 vs 길이 측정 후보 2개)에서 개념적으로 올바른 후보를 정확한 근거와 함께 선택하는 것을 확인.
- **sparse 검색은 SQL 확장 없이 애플리케이션 레벨로 구현**: 코퍼스가 223개로 작아 Cloud SQL에 별도 tsvector/한국어 형태소 분석기 확장을 추가하지 않고, 음절 bigram 토크나이저 + `rank-bm25`(BM25Okapi)로 Python에서 직접 처리. Cloud SQL 확장 설치 권한 이슈를 피할 수 있는 부수 효과도 있음.
- **Cloud SQL 권한 이슈 발견**: 기존 앱 DB 계정이 `public` 스키마에 `CREATE` 권한이 없어(Postgres 15+ 기본값) `ingest_curriculum.py`의 테이블 생성이 실패함. 최소 권한 원칙에 따라 테이블 생성은 관리자가 1회 수행하고, 앱 계정은 `SELECT, INSERT, UPDATE`만 부여받는 방식으로 진행하기로 함.
- REQ-002 SRS를 v3.0으로 갱신해 위 변경사항 전체 반영 완료(RS-000/002/003/004/005, NFR, 기술 스택, 리스크 표).

### 8.6 정슬기·박만구(2023) 논문 표 전체를 활용한 골든셋 3행 추가 (2026-08-04)

- 위 8.2에서는 이미 "없음"으로 남아있던 행 재검색 용도로만 이 논문을 썼지만, 논문의 `<표 4>`(초등 4학년 10개 단원 - 성취기준 - 관련 AI 내용 요소 전체 매핑)를 다시 검토해 신규 골든셋 행을 추가로 뽑아냈다.
- **주의**: 이 논문은 2015 개정 교육과정 기준이라 성취기준 코드가 2022 개정과 다르다. 단순 코드 치환이 아니라 성취기준 원문 내용으로 재매칭이 필요했음 (예: "자료와 가능성" 도메인이 구 `05`번 → 신 `04`번, "사각형"이 구 "변화와 관계(02)" → 신 "도형과 측정(03)"으로 도메인 자체가 재편됨).
- **채택 기준**: 골든셋은 원래도 문자 그대로 일치가 아니라 의미적 매칭을 써왔음(예: no.4 "패턴 인식"→`2수02-01`, 원문엔 "패턴"이라는 단어 자체가 없음). 이번에도 같은 기준 — "AI 개념 정의가 실제로 그 성취기준이 요구하는 활동/이해를 설명하는가" — 으로 논문의 10개 단원 AI 요소 전체를 재평가했다. 논문 자체가 12명 전문가(석사급/5년 이상 경력 교사)의 CVR 검증(항목별 평균 0.9~0.97)을 거쳤다는 점에서 LLM 자체 재검색보다 신뢰도가 높다고 판단.
- 10개 단원 중 "데이터 시각화"(막대그래프), "분류"(사각형), "예측"(꺾은선그래프) 3개는 이미 골든셋에 동일 코드로 존재 — 논문이 독립적으로 같은 매핑에 도달했다는 교차검증 근거로만 활용(8.2에 이미 반영).
- 나머지 7개 단원의 AI 요소(인공지능/학습/데이터/센서/자율주행자동차, 머신러닝/딥러닝/인공신경망/가중치, 지도학습/비지도학습/군집, 전문가시스템/지식네트워크, 시행착오/선형회귀 등)는 성취기준 자체의 내용이라기보다 "이 수학 활동을 계기로 이런 AI 개념도 소개하면 좋겠다"는 수업 설계용 창의적 연계라 골든셋 정답 근거로 쓰기엔 약하다고 판단해 반영하지 않음.
- 다만 2개 단원에서 의미적으로 방어 가능한 매칭을 찾아 **기존 골든셋 개념명을 재사용**해 grade4 사례를 추가:
  - **no.31 비교와 순서화**(기존 no.29는 grade2) → `4수01-02`. 논문의 "큰 수" 단원 AI 요소 "정렬"에서 착안 — 수의 계열 이해·크기 비교가 정렬의 개념적 전제와 일치.
  - **no.32 반복과 규칙 적용**(기존 no.30은 grade3) → 1차 매핑 `4수03-04`(밀기/뒤집기/돌리기), 논문의 "평면도형의 이동" 단원 AI 요소 "반복 구조"에서 착안. → **8.7에서 재검토 후 "없음"으로 반려** (아래 참고).
  - **no.33 의사결정트리**(신규 개념명) → `4수03-10`. 논문의 "사각형" 단원 AI 요소 "의사결정트리"에서 착안. no.2 "분류"와 같은 코드를 가리키지만 "분류"는 결과(무엇으로 분류되는가), "의사결정트리"는 과정(조건 분기로 어떻게 분류하는가)이라는 다른 측면이라 중복이 아니라고 판단.
- **1차 골든셋 상태**: 총 33행 / 있음 19 / 없음 13 / 제외 1 (no.32 반려 전 기준, 8.7에서 최종 18로 조정됨).

| **KoE5** | 26.32% | **47.37%** | **68.42%** | 68.42% |
| multilingual-e5-large | 31.58% | 42.11% | 57.89% | 63.16% |

기존 16행 기준 결론(KoE5가 R@5 기준 최우수)은 그대로 유지. 다만 이번에 새로 추가한 3행(no.31/32/33)은 4개 모델 전부에서 순위가 크게 밀림(no.31 순위 39~54위, no.32 41~77위, no.33 3~31위) — "정렬/반복적용/의사결정" 같은 절차·메타 개념은 성취기준 원문과 어휘 중복이 거의 없어 dense 임베딩이 특히 취약함을 보여줌.

**RRF 융합 후 top-20(CANDIDATE_POOL_SIZE) 생존율 직접 계산** (dense=KoE5 + sparse=BM25, `_reciprocal_rank_fusion` 재사용)

Recall@k는 dense 단독 순위였을 뿐이고, 실제 파이프라인은 `dense+sparse RRF 융합 → top-N만 LLM 리랭커에 전달` 구조라 **융합 후 top-N 밖으로 밀리면 LLM이 정답을 볼 기회 자체가 없다는 점**을 확인하기 위해 직접 계산함. 결과: 19개 중 15개(78.9%)만 top-20 생존. 특히 **no.2 "분류"(grade4, 기존 데이터, 오늘 추가분 아님)도 23위로 top-20 컷을 근소하게 놓침** — CANDIDATE_POOL_SIZE=20이 기존 골든셋 기준으로도 이미 타이트했다는 뜻.

**풀 사이즈 스윕 실험** (pool 15/20/25/30/40/50, 19행 기준 top-N 생존율)

| pool | 생존 | 생존율 | LLM 입력(pool=20 대비) |
| --- | --- | --- | --- |
| 15 | 14/19 | 73.7% | 0.75배 |
| 20(기존) | 15/19 | 78.9% | 1.00배 |
| **25** | 16/19 | 84.2% | 1.25배 |
| 30 | 17/19 | 89.5% | 1.50배 |
| 40 | 17/19 | 89.5% | 2.00배 (**30 대비 개선 없음**) |
| 50 | 18/19 | 94.7% | 2.50배 |

30→40 구간은 생존율 개선이 전혀 없어(둘 다 17/19) 무조건 키우는 게 능사가 아님을 확인. 그리고 **no.32는 pool=50까지 늘려도 82위로 끝내 못 찾힘** — 이건 풀 크기 문제가 아니라 애초에 대응되는 성취기준이 없다는 신호로 해석.

**no.32 재검토 → "없음"으로 반려**: 구 성취기준 "평면도형의 이동을 이용하여 규칙적인 무늬를 꾸밀 수 있다"(구 `4수02-05`)가 2022개정에서 독립 성취기준으로 승계되지 않은 것으로 확인됨(4수02-01~03/4수03-01~25 어디에도 없음). 1차 매핑했던 `4수03-04`는 "밀기/뒤집기/돌리기로 변화를 이해"할 뿐 "무늬 만들기"는 도메인 공통 explanation에 예시로만 스치듯 언급 — 성취기준 본문이 아님. pool=50에서도 못 찾힌 실측 결과가 이 판단을 뒷받침. no.31/no.33은 각각 48위/28위로 pool=50 안에는 들어와 개념 매칭 자체는 유효하다고 판단, 유지.

**1차 결정(보류) — CANDIDATE_POOL_SIZE: 20 → 25.** 위 생존율 표 기준으로 20→25가 비용 대비 수익이 가장 좋아 보여 일단 반영했으나, 이건 "정답이 후보 목록에 들어오는가"만 본 프록시 지표였다. 실제로 중요한 건 그 다음 단계 — **LLM 리랭커가 늘어난 후보 사이에서 정답을 제대로 골라내는가**였고, 이건 실제 Gemini 호출 없이는 알 수 없어서 `eval_poolsize_latency.py`로 직접 측정했다.

**LLM-in-the-loop 실측 (`eval_poolsize_latency.py`, 골든셋 18행 "있음", 동일 모델 gemini-flash-lite-latest, pool=20/25 각각 전체 재실행)**

| pool | Recall | 평균 지연 | 최대 지연 | NFR-002-1(2초) 초과 |
| --- | --- | --- | --- | --- |
| **20** | **61.11%(11/18)** | **2.75s** | 7.67s | 15/18 |
| 25 | 50.00%(9/18) | 4.87s | 33.48s(429 재시도 30s 대기 포함, 순수 생성시간은 ~3.48s) | 14/18 |

pool을 25로 늘렸는데도 Recall이 61.11%→50.00%로 **하락**하고 지연도 2.75s→4.87s로 **악화**됨. 행별로 보면 no.1(분류,g2)은 pool25에서 새로 맞혔지만(X→O), no.2(분류,g4)는 반대로 pool25에서 놓쳤다(O→X) — top-25는 top-20의 상위집합이라 정답 후보 자체는 두 풀 모두에 있었는데도, 후보가 5개 더 늘어나자 LLM이 오답을 골랐다. 즉 **"top-N 생존율" 개선(retrieval 단계)이 "최종 정답률" 개선(LLM 리랭킹 단계)으로 그대로 이어지지 않고, 후보(distractor)가 늘수록 LLM 리랭커의 선별 정확도가 함께 떨어져 순효과가 오히려 마이너스였다.**

**최종 결정 — CANDIDATE_POOL_SIZE: 20으로 원복.** "후보 풀 생존율"만으로 크기를 늘리는 판단은 위험하고, LLM-in-the-loop 실측 없이는 pool 크기 튜닝을 확정하면 안 된다는 게 이번 실험의 핵심 교훈. `logic.py` 원복 완료(주석에 실험 결과와 교훈 기록).

**최종 골든셋 상태**: 총 33행 / 있음 18(no.32 반려로 19→18) / 없음 14 / 제외 1.

### 8.8 임베딩 모델 선택도 dense-only Recall이 아니라 end-to-end로 재검증 (2026-08-04)

8.7에서 "후보 풀 생존율(retrieval 단계 프록시)만으로 pool size를 늘리면 안 되고 LLM-in-the-loop 실측이 필요하다"는 교훈을 얻은 직후, **같은 함정이 임베딩 모델 선택(§8.4~§8.5)에도 있다는 지적**이 나옴 — `eval_recall.py`가 측정한 Recall@k는 dense 임베딩 단독 코사인 순위일 뿐, sparse RRF 융합과 LLM 리랭커를 거친 최종 파이프라인 성능과는 별개라는 것.

`eval_embedding_e2e.py` 신설: `EMBEDDING_MODEL`을 바꿔가며 실제 `search_within_chunks`(dense+sparse RRF+LLM 리랭커) 전체를 골든셋에 돌려 end-to-end Recall/지연을 비교. E5 계열 쿼리 프리픽스(`query: `) 처리를 위해 `logic.embed_text`를 몽키패치.

**결과 (골든셋 18행, pool=20, gemini-flash-lite-latest, 동일 세트로 직접 비교)**

| dense 모델 | dense-only Recall@5(참고, §8.7 표) | **end-to-end Recall(실측)** | 평균 지연 |
| --- | --- | --- | --- |
| ko-sroberta-multitask(기존/프로덕션) | 63.16% | **61.11%(11/18)** | 2.75s |
| KoE5(dense-only 1위) | 68.42% | 55.56%(10/18) | ~2.95s(429 재시도 30s 제외) |

dense-only에서 KoE5가 더 좋았음에도 end-to-end에서는 오히려 **순손실**(no.1은 새로 맞혔지만 no.2·no.9를 새로 놓쳐 순 -1). §7/§8.4~8.5에서 "ko-sroberta → KoE5로 교체" 추천했던 건 dense-only 지표에만 근거한 것으로, 실측 결과 뒤집힘.

**최종 결정 — 임베딩 모델은 `jhgan/ko-sroberta-multitask`(기존 프로덕션 모델)를 유지.** dense-only 벤치마크(`eval_recall.py`)는 "이 임베딩이 RRF 융합에 기여할 여지가 있는가"를 보는 참고 지표로만 쓰고, 실제 모델 교체 여부는 반드시 `eval_embedding_e2e.py` 같은 end-to-end 실측으로 결정한다는 원칙을 세움. (주의: 18행·단일 실행 기준이라 LLM 샘플링 노이즈 여지는 있음 — "KoE5가 명백히 우수하다"는 근거가 사라졌다는 결론이지, "KoE5가 확정적으로 열등하다"는 강한 결론은 아님.)

### 8.3 `logic.py` 리팩터링
- `hybrid_search`에서 DB 조회 이후 로직(dense+sparse RRF+LLM 리랭킹)을 `search_within_chunks(query, chunks, embeddings)`로 분리. DB 없이 로컬 캐시로 동일 파이프라인을 재현할 수 있어 오프라인 평가/골든셋 재검색에 재사용.

### 8.4 임베딩 로컬 캐싱
- `cache_embeddings.py` 신설. 262개 청크를 여러 임베딩 모델로 미리 계산해 `app/data/embeddings_cache/*.npz`에 저장 (내일 DB 연결되면 재계산 없이 바로 upsert 가능).
- 최초 ko-sroberta-multitask / bge-m3 2개 → 리트리벌 태스크 특화 모델 검증을 위해 **KoE5, multilingual-e5-large 추가해 4파전으로 확대 진행 중** (E5 계열은 query:/passage: 프리픽스 처리 포함).

### 8.5 prefilter(dense+sparse) vs LLM-only 비교
- RS-006 1번에서 진단한 "ko-sroberta 유사도가 관련성과 무관하게 0.5~0.7에 뭉쳐 변별력이 약함"이 실제로 prefilter 무용론으로 이어지는지 의문이 제기되어, 학년군 필터만 거친 후보 전량을 곧장 Gemini에 넘기는 `llm_only` 방식과 기존 `hybrid`(dense+sparse RRF top20 → Gemini) 방식을 golden set 16개 "있음" 행으로 직접 비교 (`gemini-flash-lite-latest` 기준, 무료 티어 쿼터 제약으로 프로덕션 모델 대신 사용).
- 결과: **hybrid Recall 62.50% / 평균 지연 3.40s** vs **llm_only Recall 43.75% / 평균 지연 10.64s(최대 95.52s)**. prefilter는 토큰 예산 절약뿐 아니라 정확도도 더 높음 — 후보가 너무 많고 순위 없이 들어가면 LLM 판단 품질도 떨어지는 것으로 보임.
- 단, 두 방식 모두 NFR-002-1(2초 이내 응답)을 자주 위반(9/16, 14/16) — prefilter 여부와 별개로 별도 개선 필요.

**실제 파이프라인 end-to-end** (`eval_poolsize_latency.py`, pool=20, `gemini-flash-lite-latest`, 42행 전량)

**Recall 47.62%(20/42) | 평균 지연 4.91s | 최대 32.16s(429 재시도 1회 포함) | NFR-002-1(2초) 초과 27/42**

REQ003의 "골든셋 정확도 80% 이상" 목표에 크게 못 미침. §8.7~8.8에서 확정한 pool=20 / ko-sroberta 유지 결정 자체는 18행 기준이었고, 42행(특히 미술 반영 후 새로 늘어난 실과/AI메타개념 행들)으로 표본을 늘리자 이전엔 안 보이던 큰 갭이 드러났다.

### 9.5 원인 진단: `GRADE_TO_BANDS`의 누적 구조로 인한 검색 범위 과다 확장

`grade_to_bands`(§`app/lib/types.py`)가 누적 구조라 target_grade 5~6 질의는 G1_2+G3_4+G5_6 전부 통과 → 사실상 **코퍼스 전체(288개)** 가 무차별하게 후보가 됨(§8.7에서 223개 기준으로 이미 지적됐던 문제가 288개로 코퍼스가 커지며 더 심해짐). 9.4의 행별 결과를 보면 실패가 grade 5~6 항목, 특히 어휘 중복이 적은 실과/메타개념(의사코드, 자연어, 디지털/아날로그 등)에 몰려 있어 이 진단과 일치.

`_reciprocal_rank_fusion`과 LLM 리랭킹 프롬프트(`prompts.py`) 둘 다 후보의 `grade_band`가 질의 `target_grade`와 얼마나 가까운지는 전혀 반영하지 않음 — G1_2 청크와 G5_6 청크가 동등한 후보로 취급됨.

### 9.6 prefilter(하이브리드) vs llm_only 재실행 (42행, 완료)

§8.5의 16행 실험(hybrid 62.50% vs llm_only 43.75%, hybrid가 우세)을 42행으로 재검증.

| 방식 | Recall | 평균 지연 | 최대 지연 | NFR-002-1(2초) 초과 |
| --- | --- | --- | --- | --- |
| hybrid(prefilter) | 47.62%(20/42) | 2.14s | 6.96s | 21/42 |
| llm_only | **66.67%(28/42)** | 47.59s | 101.40s | 41/42 |

hybrid 47.62%는 `eval_poolsize_latency.py`(9.4) 결과와 정확히 일치 — 동일 파이프라인 재현성 확인. §8.5와 반대로 **llm_only가 19%p 더 높음**. 다만 llm_only는 평균 지연이 22배(47.59s vs 2.14s)에 SLA를 41/42로 사실상 항상 위반해 프로덕션에 그대로 쓸 수 없음 — **이 비교의 목적은 "뭘 배포할지 결정"이 아니라 "prefilter가 정답을 얼마나 걸러내고 있는지"를 재는 진단(ablation)** 이었고, 결과는 "많이 걸러내고 있다(약 19%p)"로 나왔다.

**역전 원인 분석 (행별 대조)**: llm_only만 성공한 7건 중 5건(no.7 데이터 수집, no.13 반복과 규칙 적용, no.14 비교와 순서화, no.18 분류(과학 도메인), no.28 분류)이 **"분류", "비교와 순서화"처럼 이름이 짧고 범용적인 개념**이었다. 예: no.28 "분류"(과학/동물, 정답 `4과02-01`)는 dense+sparse가 텍스트 유사도상 no.2 "분류"(수학/사각형, `4수03-10`) 쪽으로 끌려가 top-20 프리필터 단계에서 정답이 아예 걸러짐(no.2 자체도 hybrid·llm_only 둘 다 실패 — 두 "분류" 개념이 dense+sparse 레벨에서 구분이 안 되고 있다는 방증). llm_only는 후보 전체를 보므로 학년/문맥 정보로 그나마 맞게 골라냄.

이는 §9.5(학년군 누적 구조로 인한 검색 범위 과다 확장)와는 **별개의 원인**이다 — 학년 거리가 아니라 **개념명·성취기준 텍스트의 도메인 모호성**으로 인한 오검색이라, §9.7의 학년 가중치 처방만으로는 이 케이스가 해결되지 않을 가능성이 높다. 어제(§8.5) 16행 표본에는 이런 유형의 개념이 적어서 안 드러났던 hybrid의 약점이, 42행(특히 "2차 추가"분 20~31번대)으로 표본이 늘며 새로 노출된 것으로 해석.

### 9.7 검토 중인 해결 방안 — grade 거리 기반 가중치

팀원 제안 5개를 검토함:

1. **Soft filter/boosting**: RRF 융합(또는 dense/sparse 점수) 단계에서 `chunk.grade_band`와 `query.target_grade`가 가까울수록 가중치를 주는 방식. 기존 `grade_band` 필드를 그대로 쓸 수 있어 구현 비용이 가장 낮음.
2. **Primary/Inclusive 분리**: primary_grade 우선 검색 → 부족하면 하위 학년군 fallback. 새 메타데이터 없이 `grade_band` 필드로 바로 구현 가능. 1번과 사실상 동일한 처방을 다른 구현(연속 가중치 vs 단계적 fallback)으로 푸는 것.
3. **질의 난이도 기반 동적 필터링**: 이 시스템은 `target_grade`가 이미 명시적 입력값이라(자연어 질의의 난이도를 추정해야 하는 상황이 아님) 적용 대상이 아니라고 판단, 보류.
4. **Readability 메타데이터 추가**: `grade_band`가 이미 교육과정 원문이 확정한 정확한 학년 태그라 재추정할 필요가 없고, 한국어 가독성 지표는 기성 라이브러리도 없어 비용 대비 이득이 낮다고 판단, 기각.
5. **Two-Stage Retrieval + grade-distance penalty**: 1·2번과 같은 처방. 다만 우리 리랭커가 점수 기반(BGE-Reranker류)이 아니라 Gemini가 chunk_id 리스트를 통째로 반환하는 LLM-as-judge라 "감산 점수"는 그대로 못 씀 — (a) RRF 융합 단계에서 페널티로 반영하거나 (b) 리랭킹 프롬프트에 "질의 학년과 같은 학년군을 우선하라"는 지시문을 추가하는 식으로 변형 필요.

**판단**: 1·2·5는 사실상 동일한 처방(학년 거리 반영)이라 실질적으로 병합. §8.7에서 확인한 "후보 늘리면 생존율은 올라도 LLM이 distractor 사이에서 헷갈려 순효과 마이너스"였던 현상과 같은 근본 원인(구분 없는 후보 과다)을 정조준하고 있어, 지금까지 시도한 pool size 조정이나 임베딩 모델 교체보다 더 구조적인 해법일 가능성이 높다고 판단. 3·4번은 낮은 우선순위/기각.

**프로토타입 구현**: `logic.py`의 `search_within_chunks`에서 RRF 융합 스코어(`fused_scores`)에 `_grade_band_weight(chunk.grade_band, query_band)`를 곱해 top-N 선정에 반영. `query_band`는 `resolve_grade_bands(target_grade)[-1]`(질의가 실제로 속한 최상위 밴드), distance는 그 밴드와 청크 밴드 사이 단계 차이.

**구현 중 발견한 버그**: 첫 프로토타입 검증(`sweep_grade_weights.py`) 1행째에서 Gemini 호출이 에러 없이 3분+ 무한 대기함(429 아님, 타임아웃 자체가 없어서 네트워크 hang이 그대로 프로세스 정지로 이어짐). `logic.py`의 `_llm_rerank`에 `request_options={"timeout": 60}` 추가로 해결 — 60초 초과 시 명시적 예외로 전환되어 기존 `_with_retry` 재시도 로직이 정상 작동하게 됨(이후 §9.12에서 SDK 자체를 교체하며 타임아웃 방식도 `http_options`로 재조정됨).

### 9.8 학년 가중치 스윕 실측 (`sweep_grade_weights.py`, 42행, pool=20, `gemini-flash-lite-latest`)

"팀 제안값(0.6/0.3)을 그냥 채택"하지 않고, §8.7/8.8에서 세운 원칙("LLM-in-the-loop 실측 없이 하이퍼파라미터를 확정하지 않는다")을 그대로 적용해 후보 4세트를 동일 조건에서 실측 비교:

| 가중치(distance 0/1/2) | Recall | 평균 지연 | 최대 지연 |
| --- | --- | --- | --- |
| 1.0 / 1.0 / 1.0 (가중치 없음, §9.4의 47.62%와 별도 재측정) | 47.62%(20/42) | 1.99s | 7.18s |
| 1.0 / 0.6 / 0.3 (팀 제안값) | 52.38%(22/42) | 1.98s | 4.57s |
| **1.0 / 0.8 / 0.6 (완만)** | **64.29%(27/42)** | 2.04s | 3.65s |
| 1.0 / 0.4 / 0.15 (강함) | 57.14%(24/42) | 1.85s | 2.60s |

**핵심 발견 — 페널티가 강할수록 좋아지는 게 아니라 중간(완만)이 최적인 비단조(non-monotonic) 관계.** 강한 페널티(0.4/0.15, 57.14%)가 팀 제안값(0.6/0.3, 52.38%)보다는 나았지만, 완만한 페널티(0.8/0.6, 64.29%)보다는 오히려 낮았다. 원인으로 추정되는 것: 골든셋 정답 중 상당수가 target_grade 5~6 질의에서도 실제로는 G3_4 청크가 정답인 경우(예: no.24 그림그래프, no.26/31 목적 기반 데이터 정리 — 전부 §9.1~9.2에서 G3_4 코드로 확정)라, 페널티를 세게 걸수록 "학년 거리로 인한 오답 억제"뿐 아니라 "진짜 정답인 하위 학년군 청크"까지 같이 밀어내는 역효과가 커져 순효과가 반전된 것으로 보인다.

**최종 결정 — `_GRADE_DISTANCE_WEIGHT`를 1.0/0.8/0.6으로 확정, `logic.py` 반영 완료.** 47.62%(가중치 없음) 대비 **+16.67%p**, llm_only(66.67%, 평균 47.59s)와는 2.4%p 차이까지 좁히면서 지연은 2초대(2.04s)로 유지 — 지금까지 시도한 개선(pool size 조정, 임베딩 모델 교체) 중 순효과가 가장 컸다.

**단, §9.6에서 찾은 "도메인 모호성으로 인한 오검색"(예: "분류" 수학 vs 과학)은 이 처방으로 해결되지 않는다** — 같은 학년군 안에서는 distance=0이라 가중치 효과가 없기 때문. REQ003 목표(80%)까지는 아직 갭이 남아있고, 이 부분은 별도 처방(예: `chunk.subject`/`domain`을 활용한 도메인 신호 반영)이 필요하다.

### 9.12 팀 리뷰로 확인 — `gemini-flash-latest`가 아니라 `gemini-3.6-flash` + 팀 공용 래퍼가 맞는 프로덕션 구성 (2026-08-04)

§9.11에서 "프로덕션 모델"이라 부른 `gemini-flash-latest`가 실은 잘못된 기준이었음이 팀 리뷰로 드러남:

1. **모델**: 팀 표준은 `gemini-flash-latest`(alias)가 아니라 **`gemini-3.6-flash`(버전 고정 문자열)**. alias는 예고 후 세대가 바뀌어 NFR-001-6(재현성 — 모델 버전 고정) 요구와 충돌한다.
2. **호출 경로**: `google.genai`를 에이전트 코드에서 직접 호출하는 건 팀 규약 위반 — 전 에이전트(A1/A2/B/C/D)가 `app/lib/gemini.py`의 `generate_structured()`/`generate_text()`를 경유해야 함(재시도 계층을 이 모듈 하나로 통일하기 위함). §9.11까지 `logic.py`에 `google.genai`를 직접 붙여 넣었던 건 규약 위반이었고, `generate_structured()` 경유로 다시 고침.
3. **thinking 제어 파라미터**: gemini-3.6-flash부터 `temperature`/`top_p`/`top_k`가 deprecated(무시됨)되고, 대신 `thinking_level`(`minimal`/`low`/`medium`/`high` 열거형)로 추론량을 조절한다. §9.11에서 쓴 `thinking_budget`(정수 토큰 예산)은 구세대 API 파라미터로, `gemini-3.6-flash`에는 애초에 안 맞는 걸 실측했던 셈 — **§9.11의 thinking_budget 스윕 수치(512 등)는 전부 잘못된 모델·잘못된 파라미터 기준이라 무효.**

**정정 조치**:
- `logic.py`: `google.genai` 직접 호출 제거 → `lib.gemini.generate_structured()` 경유로 교체. `RERANK_MODEL = "gemini-3.6-flash"`, `RERANK_THINKING_LEVEL = "low"`(NFR-002-1 2초 목표를 위해 medium 기본값 대신 명시).
- `docs/curriculum_search/REQ002-교육과정검색엔진.md` v3.2: RS-004 처리 ⑤·3장 기술스택 리랭커 행의 모델명 정정, 4장 리스크표 "temperature 낮추기" 완화책 삭제(비결정성은 인정하고 reasoning으로 추적하는 쪽으로 정정), NFR-002-1에 thinking_level 기본값 주의 추가, RS-000-3 CurriculumChunk의 `embedding` 행이 테이블 컬럼 기준이며 전달 객체에는 없음을 명시.
- 실제 엔드투엔드 스모크 테스트(`search_within_chunks`, "분류" g4)로 `generate_structured()` 경유 호출이 정상 동작함을 확인(8.60s, 정답 `4수03-10` 반환).

**남은 일**: §9.11의 Recall/지연 수치(83.33%, 6.59s)는 잘못된 모델 기준이라 그대로 못 씀 — `gemini-3.6-flash` + `thinking_level="low"`로 42행 전체 재측정 필요(§9.13에서 진행).

**해석**: §9.11의 무효 수치 대비 recall은 4.76%p 낮아졌지만(83.33%→78.57%, REQ003 목표 80%에 1.43%p 못 미침 — 1행 차이), 평균 지연은 절반 이상 줄었다(6.59s→3.07s). `thinking_level="low"`가 §9.11에서 시도했던(그리고 잘못된 모델에 적용해 무효였던) thinking 예산 축소 아이디어의 실제 효과를 보여줌 — 방향은 맞았고, 이번엔 올바른 모델·파라미터로 실측해 신뢰할 수 있는 수치가 나왔다. 아직 2초 SLA는 대부분(40/42) 넘지만 6.59s보다는 훨씬 현실적인 범위.

### 9.14 `thinking_level` 3점(minimal/low/medium) 비교 후 low 채택 결정 (2026-08-04)

§9.13에 이어 `minimal`도 동일 조건(42행, pool=20)으로 재측정해 3점을 완성:

| thinking_level | Recall | 평균 지연 | 최대 지연 | 2초 SLA 초과 |
| --- | --- | --- | --- | --- |
| minimal | 80.95%(34/42) | 3.19s | 9.64s | 41/42 |
| **low(채택)** | 78.57%(33/42) | 3.07s | 8.78s | 40/42 |
| medium(모델 기본값) | 83.33%(35/42) | 6.48s | 12.01s | 42/42 |

**minimal과 low는 recall(78.57~80.95%)·지연(3.07~3.19s) 둘 다 사실상 동일 — 1행 차이는 LLM 비결정성 노이즈로 해석**(§4 리스크 "LLM 리랭킹의 비결정성" 참고, 이 모델은 재현성이 완전 보장되지 않음). 반면 **medium은 확실히 다른 지점**: recall +2.4~4.76%p를 얻는 대가로 지연이 2배 이상(6.48s, 최대 12.01s)이 됨.

**결정 — `RERANK_THINKING_LEVEL = "low"` 유지, medium 채택하지 않음.** 근거:
1. medium이 확보하는 recall 이득(42개 중 1~2행)은 REQ003 B(매핑 에이전트)의 B-06(후보 밖 반환 시 SearchResult 1순위 fallback)·B-07(재매핑 요청 처리) 덕분에 파이프라인 차원에서 이미 일부 흡수됨 — A2 단독 recall 갭이 그대로 시스템 실패로 이어지지 않음.
2. 남은 recall 갭(low 기준 REQ003 목표 대비 1.43%p)은 §9.6에서 이미 식별한 도메인 모호성 문제(예: "분류" 수학 vs 과학) 같은 걸 고치면 latency 비용 없이 메울 여지가 있음 — 모든 질의에 영구적으로 3초 이상의 지연을 추가하는 것보다 싼 해법일 가능성이 높음.
3. medium의 최대 지연(12.01s)은 사용자 체감상 "멈춘 것처럼" 보일 위험이 커 UX 리스크가 큼.

**NFR-002-1 재조정 제안**: 2초 → **3~3.5초**로 완화 제안(6.5초는 과함). `docs/curriculum_search/REQ002-교육과정검색엔진.md`에 팀 검토용으로 반영 예정(승인 전까지는 "제안" 상태로 표기).

**(2026-08-05 갱신) 팀 승인 완료 및 공지됨 — NFR-002-1 3~3.5초로 확정.** `docs/curriculum_search/REQ002-교육과정검색엔진.md` v3.3 안에 값 수정으로 반영 완료(별도 버전 안 올림).

### 9.17 정정된 모델로 `eval_prefilter_vs_llm_only.py` 재실행 — 도메인 모호성 문제 재확인 (2026-08-05)

§9.6의 "분류"(수학 vs 과학) 도메인 혼동 진단이 `gemini-flash-lite-latest` 기준이었다는 점을 감안해, 정정된 프로덕션 모델(`gemini-3.6-flash`, `thinking_level`은 모듈 기본값 `low`)로 42행 전체 재실행. 결과 캐시는 `app/data/archive_lite_model_results/`로 격리 후 재측정(같은 golden set 줄번호를 재사용하는 리스타트 캐시가 옛 lite 모델 결과를 잘못 재사용하는 걸 방지).

**타임아웃 우려 해소**: llm_only 쪽은 grade 5~6 질의에서 후보가 288개(262,947자)까지 늘어나 이전 lite 모델 기준 최대 101초까지 걸렸었음 — `_llm_rerank`의 60초 타임아웃을 넘길 위험이 있었으나, 실제로는 최대 12.90초로 끝나 문제 없었음(gemini-3.6-flash가 lite보다 대형 프롬프트에서도 더 빠름).

**결과**:

| 방식 | Recall | 평균 지연 | 최대 지연 | NFR-002-1(3.5초, 승인된 기준) 초과 |
| --- | --- | --- | --- | --- |
| hybrid | 76.19%(32/42) | 2.97s | 8.35s | 5/42(12%) |
| llm_only | 85.71%(36/42) | 4.44s | 12.90s | 29/42(69%) |

**핵심 발견 — 도메인 혼동 문제는 lite 모델의 약점이었고, 정정된 모델에서는 재현되지 않음.** §9.6에서 hybrid가 실패했던 대표 사례인 no.18 "분류(과학 도메인)"·no.28 "분류"가 이번엔 hybrid·llm_only 둘 다 정답을 맞힘. §9.6 진단 당시 근거로 든 "'분류' 수학/과학이 dense+sparse 레벨에서 구분 안 됨" 현상 자체가 사실은 리랭커(lite 모델)가 후보를 잘못 판단한 결과였을 가능성이 높음 — **§9.6~9.9에서 검토했던 "도메인 모호성 전용 처방"은 불필요한 것으로 결론.** 남은 hybrid 단독 실패 행(no.11/13/14/26/29)은 이름 모호성 패턴이 아니라 §9.9에서 이미 확인한 일반적인 prefilter 순위 밀림(top-20 밖으로 정답이 밀리는 경우)의 연장선으로 보임 — 새 처방 대상이라기보다 기존에 파악된 구조적 한계.

**hybrid 채택 근거 재정리 — recall-지연 트레이드오프가 아니라 NFR 준수 여부.** hybrid의 recall 손실(76.19% vs 85.71%, 9.52%p·4행)은 상대적으로 작지 않아(~11%) "손실이 미미하다"는 논리로는 정당화하기 약함. 대신 결정적인 건 **llm_only가 방금 팀 승인된 NFR-002-1(3~3.5초)을 10개 중 7개(69%)꼴로 위반**한다는 점 — hybrid는 12%만 위반. 즉 hybrid를 쓰는 이유는 "recall을 조금 포기하고 속도를 얻는 합리적 트레이드오프"가 아니라, **llm_only는 애초에 승인된 스펙을 통과 못 하는 배포 불가 후보**이기 때문. 이 프레이밍이 더 정확한 근거.

### 9.18 임베딩 모델 재비교 — §8.8 결론 뒤집힘, KoE5로 교체 (2026-08-05)

§8.8에서 "ko-sroberta-multitask 최종 유지"로 확정했던 건 정정 전 리랭커(lite 모델 대체) 기준이었다. §9.17에서 리랭커 정정이 도메인 모호성 진단 자체를 뒤집은 걸 보고, 같은 논리로 임베딩 모델 순위도 재검증이 필요하다는 지적이 나와 `eval_embedding_e2e.py`를 정정된 리랭커(`gemini-3.6-flash`, `thinking_level` 모듈 기본값 `low`)로 4개 모델 전체 재실행(42행, pool=20).

**결과(몽키패치 방식 실행, 1차)**:

| 임베딩 모델 | Recall | 평균 지연 | 최대 지연 |
| --- | --- | --- | --- |
| jhgan/ko-sroberta-multitask(기존 프로덕션) | 78.57% | 2.92s | 8.77s |
| BAAI/bge-m3 | 80.95% | 3.07s | 11.12s |
| **nlpai-lab/KoE5** | **83.33%** | 3.10s | 12.57s |
| intfloat/multilingual-e5-large | 76.19% | 3.09s | 10.84s |

§8.8 결론(ko-sroberta 유지)이 뒤집힘 — KoE5가 78.57%→83.33%(+4.76%p)로 가장 높고 REQ003 목표(80%)를 넘김, 지연도 NFR-002-1(3~3.5초) 이내.

**프로덕션 코드 반영**: `logic.py`의 `EMBEDDING_MODEL`을 `nlpai-lab/KoE5`로 교체. E5 계열은 query:/passage: 프리픽스가 없으면 성능이 크게 떨어진다고 알려져 있어, 기존에 eval 스크립트에만 있던 프리픽스 로직(`QUERY_PREFIX`/`PASSAGE_PREFIX`)을 `embed_text()`에 `is_query` 파라미터로 정식 이식(기본값 `is_query=False`라 `ingest_curriculum.py`의 청크 임베딩 호출은 그대로 passage 프리픽스 적용, 질의 임베딩만 `search_within_chunks`에서 `is_query=True`로 명시).

**재현성 검증 중 발견한 문제 — 단일 실행 노이즈가 생각보다 큼.** `eval_embedding_e2e.py`는 자체 몽키패치로 `embed_text`를 덮어써서 실제로는 방금 고친 프로덕션 코드 경로를 안 타고 있었음 — 몽키패치를 걷어내고 진짜 `embed_text(is_query=True)` 경로로 KoE5를 다시 42행 전체 재실행한 결과 **83.33%가 아니라 78.57%**가 나옴(35→33개 정답, ko-sroberta의 예전 수치와 정확히 동일). dense 임베딩 계산(프리픽스 포함)은 두 실행이 완전히 동일한 방식이라 재현 안 되는 부분은 리랭커(`gemini-3.6-flash`)의 비결정성뿐으로 추정 — **동일 조건 재실행만으로 4.76%p(2행)가 노이즈로 흔들릴 수 있다는 뜻.** 그래서 "KoE5가 ko-sroberta보다 확실히 더 낫다"는 주장의 통계적 근거는 이 세션 내에서는 약함(반복 시행 없이는 확정 불가) — 다만 dense-only 벤치마크·두 차례 end-to-end 실측(83.33%, 78.57%) 어디에서도 KoE5가 ko-sroberta보다 나쁘게 나온 적은 없어 "최소 동등, 상회할 가능성"으로 교체를 결정.

**최종 결정 — `EMBEDDING_MODEL = "nlpai-lab/KoE5"`로 교체 확정, 대표 수치는 83.33%로 기록(최초 측정치, 팀 공유용).** 실제로는 78.57~83.33% 사이에서 리랭커 비결정성에 따라 흔들릴 수 있다는 점을 남겨둠 — 이후 recall이 예상과 다르게 나오면 이 노이즈 범위부터 의심할 것.

### 9.19 임베딩 모델 교체 후 hybrid vs llm_only 재검증 (2026-08-05)

§9.17의 hybrid vs llm_only 비교(hybrid 76.19%)는 임베딩 모델을 KoE5로 바꾸기 전(ko-sroberta 기준)이었다 — llm_only는 애초에 임베딩을 안 써서 무관하지만, hybrid는 dense 신호를 쓰므로 재검증이 필요했다. `eval_prefilter_vs_llm_only.py`를 KoE5로 재실행(`EMBEDDING_CACHE`를 `nlpai-lab__KoE5.npz`로 명시 — 이 스크립트가 캐시 경로를 하드코딩하고 있어 그냥 돌리면 쿼리(KoE5, 1024차원)와 후보(ko-sroberta 캐시, 768차원) 차원이 안 맞을 뻔함, 실행 전에 확인해서 방지).

| 방식 | Recall(ko-sroberta, §9.17) | Recall(KoE5, 재검증) | 평균 지연 | NFR-002-1(3.5초) 초과 |
| --- | --- | --- | --- | --- |
| hybrid | 76.19%(32/42) | **83.33%(35/42)** | 3.29s | 12/42(29%) |
| llm_only | 85.71%(36/42) | 88.10%(37/42) | 4.22s | 28/42(67%) |

hybrid의 recall이 KoE5로 76.19%→83.33%로 오르며 llm_only와의 격차가 9.52%p→**4.77%p**로 줄었다 — `eval_embedding_e2e.py`의 독립 측정치(83.33%)와 정확히 일치해 교차검증됨. 다만 hybrid의 NFR-002-1(3.5초) 위반율은 12%→29%로 다소 늘어남(KoE5가 ko-sroberta보다 약간 무거운 모델). §9.17의 결론(hybrid 채택, llm_only는 NFR 위반율이 훨씬 높아 배포 불가)은 그대로 유지됨 — hybrid가 38%p 낮은 위반율(29% vs 67%)로 여전히 명확한 우위.

## 10. 오케스트레이터(D) 통합 계약 불일치 해결 (2026-08-06)

PR #22가 머지된 뒤 main을 당겨보니 D(김준명)의 `orchestrate.py`가 실제로 머지돼 있었다. D가 스텁을 실제 모듈 import로 교체하다가 A2 쪽에서 계약 불일치 2건을 발견해 `[A2 통합 요청] orchestrate.md` 문서로 정리해 보내왔다.

### 10.1 발견된 불일치

1. **함수명**: 스텁은 `search_curriculum`을 기대하는데 실제는 `hybrid_search`. 이건 A1(`collect_concept` vs `analyze_concept`)·B(`map_concept` vs `map_curriculum`)도 동일하게 어긋나 있어서(C만 우연히 일치) A2만의 문제가 아니었고, D도 "import에서 흡수 가능"이라며 문제 삼지 않음 — **이름은 그대로 유지**(`hybrid_search`가 테스트·eval 스크립트·REQ002 문서·본 기록 전반에 이미 쓰이고 있고, "하이브리드 검색인데 이름과 실제가 다르다"던 §2의 옛 문제를 정정한 의미 있는 이름이라 바꿀 이유가 없다고 판단).
2. **sync/async 불일치(진짜 문제)**: `run_pipeline()`이 동기 함수인데 `hybrid_search`는 `async def`(DB 조회·임베딩을 `asyncio.to_thread`로 처리하느라). 그대로 갈아끼우면 코루틴 객체만 받고 `len()`에서 깨짐. A1·B의 실제 함수는 둘 다 동기라 문제없었음 — A2만의 이슈.
3. **예외 소실**: `_llm_rerank`/`hybrid_search` 내부에서 `GeminiError`/`DatabaseError`를 잡아 `CurriculumSearchError`(RuntimeError 직속)로 다시 감싸고 있어서, 오케스트레이터의 전역 핸들러 `except (GeminiError, DatabaseError)`를 못 타고 500 에러로 새어나감. REQ-005 "파이프라인 전체가 중단되지 않도록 방어" 요건 위반.

### 10.2 D의 근거와 제안

D는 `hybrid_search` 내부에 `await` 지점이 전부 `asyncio.to_thread(...)`뿐이고 `gather`/`create_task` 같은 실제 동시성이 없다는 점(코드를 직접 읽고 지적함)을 근거로, `asyncio.run()`으로 감싸는 임시방편 대신 **동기 코어 + 얇은 async 래퍼** 구조를 제안했다:

```python
def search_curriculum(query: SearchQuery) -> list[SearchResult]:
    """동기 진입점. 내부 블로킹 호출을 to_thread 없이 직접 실행한다."""
    ...

async def hybrid_search(query: SearchQuery) -> list[SearchResult]:
    """기존 async 호출자 호환용 래퍼."""
    return await asyncio.to_thread(search_curriculum, query)
```

`asyncio.run()`으로 감싸는 안을 쓰지 않은 이유: `app/main.py`의 라우트가 지금은 동기라 당장은 동작하지만, E가 나중에 `async def`로 바꾸는 순간 "asyncio.run() cannot be called from a running event loop"로 터진다. 오케스트레이터 전체를 async로 전환하는 대안도 있었지만 `main.py`까지 파급 범위가 커서 이 시점엔 과하다고 판단해 기각.

예외 소실 건은 D가 3가지 대안((a) 원본 예외 그대로 올리기 (b) `CurriculumSearchError`를 `GeminiError` 하위로 편입 (c) 오케스트레이터가 `CurriculumSearchError`까지 잡도록 핸들러 확장)을 제시하고 (a)를 권장 — DB 실패를 Gemini 계열로 분류하는 (b)는 어색하고, (c)는 오케스트레이터가 A2 모듈을 예외 타입 때문에 import하게 돼 결합도가 올라간다는 이유.

### 10.3 A2 쪽 구현

D의 제안을 그대로 채택했다. 구현 시 로직 중복을 피하려고, RRF 융합·학년 가중치·후보 풀 선정 같은 순수 계산(`_rank_candidates`)과 결과 조립(`_assemble_results`)을 sync/async 양쪽이 공유하도록 추출했다 — 실제로 sync/async 사이에서 다른 건 임베딩 호출(`_embed_text_sync` vs `embed_text`)과 리랭킹 호출(`_llm_rerank_sync` vs `_llm_rerank`)뿐이고, 후자는 아예 전자를 `asyncio.to_thread`로 감싸는 한 줄로 축소했다.

`search_within_chunks`(async, DB 없이 로컬 캐시로 오프라인 평가하는 eval 스크립트 4개+`sweep_grade_weights.py`가 재사용 중)는 시그니처·동작을 그대로 유지하고, `search_within_chunks_sync`를 신규 병렬 추가하는 방식을 택했다 — eval 스크립트를 건드리지 않기 위함.

예외 처리는 D 권장안(a)대로 `raise ... from exc`를 걷어내고 `logger.warning(...)` 로깅만 남긴 뒤 원본 예외를 그대로 올리도록 `_llm_rerank_sync`/`search_curriculum` 둘 다 수정했다.
