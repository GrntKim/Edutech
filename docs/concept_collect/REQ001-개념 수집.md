## 1. 프로젝트 개요

| 항목 | 내용 |
| --- | --- |
| 프로젝트명 | 교육과정 기반 AI 개념 교육 지원 시스템<br>(기존: 성취기준 연계 에듀테크 교수학습과정안·활동지 자동 생성 시스템) |

| 작성일 | 2026-08-02 (최종 수정 2026-08-05) |

본 문서는 사용자가 입력한 **AI 개념명(분류·예측·패턴 인식 등)과 대상 학년**을 입력받아, 개념을 **구조화된 정의(StructuredConcept)** 로 변환하고 이를 **교육과정 검색에 적합한 쿼리(SearchQuery)로 재작성**하는 기능의 요구사항을 정의한다. 본 모듈은 전체 파이프라인의 **진입점**이며, 출력은 A2(교육과정 검색 엔진)의 입력으로 직접 사용되고, 구조화 필드 일부는 C(교안 생성)·D(검증)에서도 참조된다.

**본 모듈의 목적(v1.1 재정의)**

1차 피드백에서 본 프로젝트의 정체성이 "교안 생성 서비스"가 아닌 **"기존 교과목을 활용해 AI 개념을 학생 눈높이에 맞게 설명하도록 지원하는 시스템"** 으로 확정되었다. 이에 따라 본 모듈의 목적도 "개념 정보를 모으는 것"이 아니라, **"AI 개념을 학생 눈높이로 설명하기 위한 판단 재료를 확보하는 것"** 으로 재정의한다.

피드백 4번은 본 프로젝트가 해결할 핵심 문제를 다음과 같이 규정했다.

> 학생 수준에 맞게 AI 개념을 설명할 기준이 없다. (예: Feature, Vector, Decision Boundary를 그대로 설명하면 초등학생은 이해할 수 없다)
> 

이 문제는 파이프라인 후단이 아니라 **본 모듈에서 1차적으로 다루어진다.** 어떤 용어가 학생에게 그대로 노출되면 안 되는지(`caution_terms`), 개념의 어떤 부분이 왜곡 없이 반드시 보존되어야 하는지(`core_mechanism`)를 판별해 후단에 전달하는 것이 본 모듈의 핵심 책임이다.

**핵심 설계 원칙**

- **LLM 기반 생성 모듈(v1.5 수정)**: 본 모듈은 Gemini 호출을 통한 판단·생성을 수행하므로 "에이전트"로 표기하는 것이 정확하다. 대신 출력 자유도는 스키마로 강하게 제약한다. 다만 A1의 생성은 **개념 자체를 새로 만드는 것이 아니라 고정 스키마의 필드를 채우는 작업**이며, 카테고리는 화이트리스트로 제한된다는 점에서 자유 생성과 구별된다.
- **구조화 출력 강제**: 자유 서술문을 반환하지 않는다. 모든 출력은 고정된 Pydantic 스키마를 통과해야 하며, 검증 실패 시 재시도한다.
- **개념 정의와 검색 쿼리의 분리**: 개념 자체의 정의는 학년과 무관하게 학술적으로 정확하게 생성하고, **학년 의존적인 어휘 조정은 검색 쿼리 재작성 단계에서만** 수행한다.
- **도메인 갭 선제 완화**: AI 전문 어휘("특징 벡터", "레이블")를 초등 교육과정 어휘("기준", "이름 붙이기", "규칙 찾기")로 번역한 쿼리를 함께 생성하여, A2의 임베딩 검색 Recall을 A1 단에서 끌어올린다.
- **역할 경계 준수**: 본 모듈은 "무엇을 설명해야 하는가"의 **재료**만 구조화한다. 학생에게 제시될 비유·활동 문장 생성은 C, 학년 제약 위반 검증은 D의 책임이며 A1은 이를 침범하지 않는다.
- **환각 억제**: 개념 카테고리는 화이트리스트로 제한하고, 미지원·모호 입력은 임의 해석 없이 명시적으로 실패를 반환한다.
- **설명 기준의 명시화(v1.1 추가)**: "학생 눈높이"를 주관적 판단에 맡기지 않고, `caution_terms`(노출 금지 용어)와 `core_mechanism`(왜곡 불가 핵심 원리)이라는 **명시적 데이터**로 후단에 전달한다. 피드백 6번이 요구한 D의 "AI 개념 왜곡 여부" 검증은 이 필드를 기준으로 수행된다.

**하위 기능 구성**

- RS-000: 데이터 모델 정의 (`schema.py`)
- RS-001: 개념 입력 정규화 및 유효성 검증 (`logic.py`)
- RS-002: 구조화된 개념 정의 생성 (`logic.py`, `prompts.py`)
- RS-003: 교육과정 검색용 쿼리 재작성 (`logic.py`, `prompts.py`)
- RS-004: 출력 스키마 검증 및 A2 인터페이스 (`schema.py`, `logic.py`)
- RS-005: 개념 정의 품질 평가

### 0. 데이터 모델 정의 (RS-000)

본 에이전트의 입출력 타입을 정의한다. 각 모델은 **Pydantic** 모델로 구현하며, **모든 타입의 정본은 `app/lib/types.py`에 단일 정의한다.**

**`schema.py`의 역할(v1.5 명시)**

`app/agents/concept_collect/schema.py`는 **자체 타입을 정의하지 않는다.** `app/lib/types.py`에 정의된 타입(`ConceptCategory`, `ConceptInput`, `StructuredConcept`, `ConceptCollectResult`, `SearchQuery`)을 A1 모듈 내부에서 참조하기 편하도록 **재수출(re-export)하는 역할만 수행**한다. 따라서 다음이 성립한다.

- 데이터 계약의 정본은 항상 `lib/types.py`이며, `schema.py` 변경만으로 계약이 바뀌지 않는다.
- A1 전용 중간 구조는 현재 존재하지 않는다. 향후 필요해질 경우 이 파일에 정의하되, 타 모듈에 노출되는 타입은 반드시 `lib/types.py`로 승격한다.
- 본 장(RS-000)의 표는 `lib/types.py` 정의를 A1 관점에서 서술한 것이며, 표와 코드가 충돌할 경우 **코드를 정본으로 한다.**

#### RS-000-1. ConceptCategory (열거형)

| 값 | 설명 | 활성화 단계 |
| --- | --- | --- |
| CLASSIFICATION | 분류 | 1단계 |
| PREDICTION | 예측 | 1단계 |
| PATTERN_RECOGNITION | 패턴 인식 | 1단계 |
| CLUSTERING | 군집화 | 1단계 |
| GENERATION | 생성 | 2단계 |
| RECOMMENDATION | 추천 | 2단계 |

**1단계 활성 카테고리 상수(v1.5 명시)**: 위 표의 "1단계" 4종은 `lib/types.py`에 `ACTIVE_CATEGORIES: frozenset[ConceptCategory]`로 구현되어 있다. A1은 이 상수를 화이트리스트로 사용하며(RS-001), 2단계 확장 시 코드 로직 변경 없이 이 상수에 값을 추가하는 것으로 대응한다.

**(v1.7 참고)** `StructuredConcept.category`는 위 6종 중 하나를 반드시 반환해야 하는 **필수 열거형**이다. 따라서 화이트리스트가 실제로 거르는 대상은 2단계 2종(GENERATION·RECOMMENDATION)에 한정된다. 열거형에 없는 개념(예: "특징 추출")이 입력되어도 모델은 6종 중 가장 근사한 값을 선택하므로 **거부되지 않고 오분류될 수 있다.** 이 점은 5-1의 "지원 AI 개념어 범위" 쟁점과 직결된다.

#### RS-000-2. ConceptInput

사용자(웹 UI, E 담당) → A1으로 전달되는 입력 스키마.

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| raw_concept_name | str | 사용자 자유 입력 개념명 (예: "분류", "머신러닝의 분류") |
| subject_hint | Subject | None | 과목 힌트. **(v1.6 확정)** 1단계에서는 웹 폼에 노출하지 않으며 E가 항상 `None`을 명시적으로 채워 전달한다. A1은 이 값을 참조하지 않고 `SearchQuery`로 전재만 하며, A2가 전 과목 교차 검색을 수행한다. 필드는 2단계(재생성 시 과목 제한) 확장을 위해 유지 |

**대상 학년(`target_grade`)의 수신 경로 — 정본 확정(v1.5)**

`target_grade`는 `ConceptInput`이 **아니라** `PipelineContext`로 전달받는다. `analyze_concept()`의 시그니처는 `(concept_input: ConceptInput, context: PipelineContext)`이며, 학년 값은 항상 `context.target_grade`를 참조한다.

- **근거**: `lib/` 공통 모듈 머지 공지(2026-08-03) — "각자 함수 시그니처에 `context: PipelineContext` 인자를 포함해주세요. `target_grade`는 이 경로로 전달됩니다."
- **설계상 이유**: `target_grade`는 A1이 생성하는 값이 아니라 사용자 최초 입력을 여러 단계가 공유하는 전역값이다. 개별 에이전트의 입력 스키마에 중복 보유하면 값이 어긋날 때 조용히 오동작한다.
- **구현 상태**: `logic.py`는 `context.target_grade`만 참조하며 `concept_input.target_grade`를 읽는 코드는 존재하지 않는다(2026-08-04 확인).
- **잔여 이슈**: `lib/types.py`의 `ConceptInput`에는 `target_grade` 필드가 아직 존재한다. A1은 이 값을 참조하지 않으나, 필드 자체의 존치 여부와 D(REQ-005) VALID-000-2의 서술 정정은 팀 확인이 필요하다(5-1 미결 항목 참조).

#### RS-000-3. StructuredConcept

A1의 핵심 산출물. 개념 1건에 대한 구조화된 정의.

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| concept_name | str | 정규화된 표준 개념명 |
| category | ConceptCategory | 개념 대분류 |
| one_line_definition | str | 한 문장 정의(학술적 정확성 기준, 학년 비종속) |
| core_mechanism | str | 동작 원리 서술 (2~4문장) |
| key_operations | list[str] | 개념이 요구하는 핵심 사고·조작 (예: "기준에 따라 나누기", "규칙 찾기", "비교하기") |
| prerequisite_ideas | list[str] | 이해에 필요한 선행 아이디어(수학·과학 일반 어휘로 표현) |
| everyday_examples | list[str] | 초등 학습자가 접할 수 있는 일상 사례 |
| caution_terms | list[str] | **학생에게 그대로 노출되면 안 되는 전문 용어** (예: Feature, Vector, Decision Boundary). 피드백 4번의 핵심 문제에 대한 직접 대응 필드.<br>**소비처(v1.3 확정): D의 VALID-001.** D가 보유한 자체 금지 용어 리스트와 **합집합**으로 검증한다. B의 `MappingResult`를 경유해 C로 전달하지 않는다 |

**v1.1 추가 검토 항목 (팀 합의 전, 미구현)**

| 필드 | 타입 | 설명 | 상태 |
| --- | --- | --- | --- |
| common_misconceptions | list[str] | 학생이 해당 개념에서 흔히 갖는 오개념 (예: "분류는 사람이 정한 기준 없이 컴퓨터가 알아서 나누는 것") | 피드백 8번의 "오개념 및 보충 설명 자동 생성" 대응. A1 생성 vs C 생성 중 담당 결정 필요 |

#### RS-000-4. SearchQuery

A2로 전달하는 검색 요청 스키마. **REQ-002 RS-000-4와 동일 정의**이며 `lib/types.py`의 단일 정의를 공유한다.

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| concept_name | str | 정규화된 AI 개념명. 구현상 `StructuredConcept.concept_name`(LLM 생성값)을 그대로 전재한다 |
| concept_definition | str | RS-003의 쿼리 재작성 결과(임베딩 대상 텍스트) |
| target_grade | int | 대상 학년(1~6). `PipelineContext.target_grade`를 그대로 전재. **(v1.7) 현재 `Field(ge=1, le=6)` 제약이 없음 — 5-1 참조** |
| top_k | int | 반환할 후보 수 (기본값 15) |

#### RS-000-5. ConceptCollectResult

A1의 최종 반환 객체. D(오케스트레이션)가 다음 단계로 전달한다.

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| concept | StructuredConcept | 구조화된 개념 정의 |
| search_query | SearchQuery | A2 입력용 검색 쿼리 |
| model_version | str | 사용한 Gemini 모델 식별자 |
| prompt_version | str | 프롬프트 템플릿 버전 태그 |
| retry_count | int | 스키마 검증 실패로 인한 재시도 횟수. **(v1.7)** 재시도 소진 시에는 본 객체가 생성되지 않고 예외가 전파되므로, 기록되는 것은 성공 케이스에 한한다 |
| status | `Literal["success", "unsupported_concept", "ambiguous_input"]` | 처리 결과 상태. **자유 문자열이 아닌 리터럴 타입으로 제약(v1.5 정정)** |

**`status`를 `Literal`로 제약하는 이유(v1.5)**: D의 ORCH-001이 이 값으로 파이프라인 진행 여부를 분기하므로(`success`가 아니면 이후 단계 미호출), 자유 문자열이면 오타가 타입 검사에서 걸러지지 않고 런타임에 조용히 통과한다. 세 값은 `lib/types.py`에 리터럴로 고정되어 있으며, 값 추가 시 D와 사전 합의한다.

### 1. 개념 입력 정규화 및 유효성 검증 (RS-001)

LLM 호출 이전에 결정론적으로 처리 가능한 검증을 먼저 수행하여, 불필요한 API 호출과 환각 가능성을 차단하는 것이 본 절의 **목표 설계**다. **(v1.7) 현재 구현은 이 설계에 도달하지 않았다.** 아래 표에 항목별 구현 상태를 병기한다.

| 항목 | 내용 | 구현 상태 | 비고 |
| --- | --- | --- | --- |
| 입력 | `ConceptInput`(raw_concept_name, subject_hint) + `PipelineContext`(target_grade) | ✅ 구현 | E(폼)와 필드명 합의 완료 |
| 처리 ① | 공백·특수문자 정리 | ❌ **미구현** | `raw_concept_name`을 그대로 프롬프트에 전달 중 |
| 처리 ② | 동의어 사전 기반 표준 개념명 매핑(예: "카테고리 분류"·"classification" → "분류") | ❌ **미구현** | 담당 주체 미확정(5-1 참조). 사전 관리 위치도 미정 |
| 처리 ③ | `context.target_grade` 범위(1~6) 검증 | ❌ **미구현** | 5-1 신규 리스크 항목 참조 |
| 처리 ④ | `ACTIVE_CATEGORIES` 화이트리스트 대조 | ⚠️ **구현되었으나 위치 상이** | 문서 설계는 LLM 호출 **이전**이나, 실제 구현은 RS-002의 구조화 출력 **이후** `concept.category`를 대조한다 |
| 출력 | (목표) 정규화된 개념명 + ConceptCategory 후보 | ❌ **미구현** | 현재 RS-001에 해당하는 독립 출력이 없으며, `category`는 RS-002의 LLM이 생성한다 |
| 예외 처리 | LLM이 반환한 `category`가 `ACTIVE_CATEGORIES`에 없으면 `unsupported_concept` 반환 | ✅ 구현 | RS-003을 호출하지 않아 Gemini 호출 1회를 절약한다. 단 이때 `SearchQuery.concept_definition`은 **빈 문자열**로 채워져 반환됨(5-1 개념어 범위 쟁점과 연동) |
| 예외 처리 | 학년 범위 밖 입력 즉시 거부 | ❌ **미구현** | 처리 ③ 미구현에 따름 |

**(v1.7) "미분류" 서술 삭제 근거**: 기존 예외 처리 항목의 "화이트리스트 미매칭 시 LLM에 1회 분류 위임, 그래도 미분류면 `unsupported_concept` 반환"은 성립하지 않는다. `StructuredConcept.category`는 필수 열거형이므로 모델은 항상 6종 중 하나를 반환하며, "미분류" 상태 자체가 발생하지 않는다. 실제 동작은 위 표와 같이 **반환된 category와 `ACTIVE_CATEGORIES`의 대조 1회**뿐이다.

### 2. 구조화된 개념 정의 생성 (RS-002)

| 항목 | 내용 | 핵심 포인트 | 비고 |
| --- | --- | --- | --- |
| 입력 | 정규화된 개념명, ConceptCategory 후보 | 학년 정보는 이 단계에서 사용하지 않음 | 학년 비종속 정의 원칙 |
| 처리 | `prompts.py`의 고정 템플릿 + `lib/gemini.py`의 `generate_structured(prompt, StructuredConcept)` 호출로 필드 일괄 생성. **`thinking_level="low"` 고정**, 출력 언어·문장 수·리스트 개수 상한을 프롬프트로 제약 | 자유 서술 금지, 필드 단위 생성 | `lib/gemini.py` 공통 래퍼 사용(`google.genai` 직접 호출 금지) |
| 출력 | StructuredConcept | RS-003·C·D에서 참조 | `key_operations`가 검색 품질에 가장 큰 영향 |
| 예외 처리 | **스키마 검증 실패(`GeminiSchemaError`) 시 동일 프롬프트로 최대 1회 재시도**, 재시도도 실패하면 예외를 D(오케스트레이터)로 전파 | 부분 필드 누락 상태로 다음 단계 전달 금지 | 재시도 횟수는 `ConceptCollectResult.retry_count`에 기록(성공 케이스 한정) |

**재시도 책임 구분(v1.5 명시)**

| 구분 | 처리 주체 | 대상 |
| --- | --- | --- |
| API 실패(타임아웃, 429 등) | `lib/gemini.py` 공통 래퍼(E 소유) | 네트워크·쿼터 계열 오류 |
| 스키마 검증 실패(`GeminiSchemaError`) | **A1(`logic.py`)** | 모델이 `StructuredConcept` 형식을 지키지 못한 경우 |
| 검증 실패에 따른 교안 재생성(최대 3회) | D의 ORCH-002 | 본 모듈과 무관(대상이 C의 교안) |

**재시도 1회로 확정한 근거(v1.5)**: ① 무료 등급 쿼터가 분당 5회/일 20회로 실측되어(4장 리스크) 호출 1회의 비용이 크다. ② NFR-001-3이 "재시도 없이 스키마 통과 95% 이상"을 목표로 하므로 재시도가 상시 발생하는 상황을 전제하지 않는다. ③ 1차 실패가 2차에서 회복될 확률에 비해 2차 실패가 3차에서 회복될 확률은 현저히 낮으며, 이 경우 원인은 대개 프롬프트 자체에 있어 재시도로 해결되지 않는다. ④ 재시도 소진 시에도 D의 ORCH-001 예외 처리(공통 에러 핸들러)가 사용자 응답을 보장한다.

### 3. 교육과정 검색용 쿼리 재작성 (RS-003)

A2 문서에서 최대 리스크로 지목한 **AI 어휘 ↔ 초등 교육과정 어휘 도메인 갭**을 완화하는 핵심 단계다.

| 항목 | 내용 | 핵심 포인트 | 비고 |
| --- | --- | --- | --- |
| 입력 | StructuredConcept, `context.target_grade` | 학년 의존 처리는 이 단계에서만 수행 | - |
| 처리 | ① `key_operations`·`prerequisite_ideas`를 성취기준 문체(예: "~을 분류할 수 있다", "~의 규칙을 찾을 수 있다")로 변환 → ② 전문 용어를 교육과정 어휘로 치환 → ③ 대상 학년 수준 어휘로 조정 → ④ 단일 `concept_definition` 문자열로 병합. `lib/gemini.py`의 `generate_text()` 경유 | 개념명이 아닌 **조작·행위 중심** 서술로 작성 | 성취기준 문체 모방이 임베딩 유사도에 유리 |
| 출력 | SearchQuery (concept_name, concept_definition, target_grade, top_k=15) | A2의 임베딩 입력 | 계약 스키마 준수 필수 |
| 예외 처리 | **(v1.7 — 목표 설계, 미구현)** 재작성 결과가 원문 용어를 그대로 복사한 경우(치환 실패) 1회 재생성. 길이 상한(권장 300자) 초과 시 절삭 대신 재생성.<br>**현재 구현은 `generate_text()` 결과에 `.strip()`만 적용해 `SearchQuery`에 그대로 사용하며, 치환 실패 검사·길이 검사·재생성이 모두 없다.** | 과도한 길이는 임베딩 희석 유발 | 길이 상한은 RS-005 실험으로 확정 |

### 4. 출력 스키마 검증 및 A2 인터페이스 (RS-004)

| 항목 | 내용 | 핵심 포인트 | 비고 |
| --- | --- | --- | --- |
| 입력 | StructuredConcept, SearchQuery | - | - |
| 처리 | Pydantic 모델 검증(필수 필드·타입·값 범위) → ConceptCollectResult 조립 → 모델·프롬프트 버전 태깅 | 파이프라인 밖으로 나가는 모든 객체는 검증 통과분만 허용 | `app/agents/orchestrate.py`(D)가 호출 |
| 출력 | ConceptCollectResult | D → A2 순으로 전달 | 1주차 내 A2·B와 계약 확정 |
| 예외 처리 | 검증 실패 시 상태 코드와 실패 필드명을 포함한 에러 반환, 부분 성공 반환 금지. Gemini 타임아웃·쿼터 초과는 `lib/gemini.py` 공통 재시도 로직에 위임 | 실패는 조용히 넘기지 않고 D에 명시적으로 전달 | 사용자 노출 문구는 E와 협의 |

**(v1.7 참고)** 위 "값 범위" 검증은 Pydantic 필드 제약에 의존한다. 현재 `SearchQuery.target_grade`에는 제약이 없어 이 단계에서 학년 값이 걸러지지 않는다(5-1 참조).

### 5. 개념 정의 품질 평가 (RS-005)

| 항목 | 내용 | 핵심 포인트 | 비고 |
| --- | --- | --- | --- |
| 입력 | **A1 자체 골든셋**(AI 개념-정답 단원 쌍, 20~30개) | 팀 결정(2026-08-03)에 따라 A1·A2·B가 각자 골든셋을 독립 관리한다. 경로·포맷 통일은 강제하지 않음 | A1 골든셋 경로: `app/agents/concept_collect/golden_set.json`(예정). 쉬운 케이스·도메인 갭 케이스 혼합 배치 |
| 처리 | ① 개념 정의 정확성 사람 검수(오류·환각 유무) ② 쿼리 재작성안별 A2 Recall@15 비교 실험(원 개념명 그대로 vs 재작성본) ③ 스키마 1회 통과율 측정 | 재작성의 효과를 **정량 수치로 입증**하는 것이 목표 | ①③은 A2 구현과 무관하게 측정 가능하며, ②만 A2에 의존한다 |
| **(v1.4) 1차 실측** | **개념 간 쿼리 중복 문제 발견 및 수정.** 초기 프롬프트로 생성한 "패턴 인식" 쿼리에 "분류할 수 있다"·"무리 짓다" 등 분류 개념의 표현이 포함되어, "분류" 쿼리와 거의 동일한 문장이 생성됨. 골든셋상 두 개념의 정답 단원은 서로 다름(분류=4수03-10 사각형 분류 / 패턴 인식=4수02-01 변화 규칙)이므로 오검색 위험이 있었음.<br>**원인**: 프롬프트의 좋은 예시가 "분류" 1건뿐이어서 모든 개념이 분류 문체로 수렴.<br>**조치**: ① 개념별 고유 표현 명시(분류=나누다/묶다, 패턴인식=규칙/반복/변화, 예측=짐작하다, 군집화=비슷한 것끼리) ② 골든셋 정답 원문 기반 예시를 3건으로 확대 ③ 실패 사례를 나쁜 예시로 명시.<br>**결과**: 패턴 인식 쿼리에서 분류 계열 표현이 제거되고 "변화 규칙" 중심으로 재생성됨. 정량 Recall 측정은 A2 검색 구현 완료 후 진행 예정 | 검색 미구현 상태에서도 **쿼리 구별성**은 선행 검증 가능 | DB 미구축으로 Recall 측정은 대기 중 |
| 출력 | 개념 정확성 검수 리포트, 쿼리 전략별 Recall@15 비교표, 스키마 통과율 | A2·B 리포트와 나란히 제시하되, **서로 다른 골든셋 기준임을 반드시 병기**한다(수치 직접 비교 금지) | 동일 기준 비교가 필요해지면 그 시점에 팀 재논의 |
| 예외 처리 | Recall 목표 미달 시 프롬프트 수정 후 재측정, 3회 이상 개선 없으면 A2의 hybrid keyword(BM25) 도입 논의로 전환 | A1 단독 튜닝에 매몰되지 않도록 종료 조건 설정 | A2와 공동 판단 |

**프롬프트 개선 방법론 기록(v1.5)**: 위 1차 실측에서 규칙을 여러 줄 추가하는 것보다 **실제 실패 사례를 "나쁜 예시"로 프롬프트에 명시하는 방식**이 즉각적인 개선 효과를 보였다. 이후 프롬프트 수정 시 이 방식을 우선 검토한다.

## 5. 인터페이스 합의 사항

| 대상 | 합의 항목 | 기한 |
| --- | --- | --- |
| A2 (박지민) | `SearchQuery` 필드·타입, `top_k` 기본값, 쿼리 재작성 형식<br>**(v1.2)** A2 v3.0(dense+sparse+LLM 리랭킹) 전환에 따른 `SearchQuery` 계약 유효성 재확인. sparse(BM25) 도입 시 쿼리 재작성에 교육과정 원문 용어를 더 적극 포함할지 협의<br>**(v1.7 확인 요청)** A2 v3.0부터 `concept_name`이 BM25 대상에 포함되므로 **표기 형태를 A2가 지정**해줄 것("패턴 인식" vs "패턴인식", 영문 병기 여부). `concept_name`은 LLM 생성값이므로 A1이 프롬프트로 형태를 고정할 수 있다 | 1주차 |
