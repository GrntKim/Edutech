## 2. 아직 남아있는 이슈

### 2-1. [미해결, 08-03과 동일] B 출력 `analogy` vs C 입력 `analogy_text`

B(REQ003 v2.0) 출력 필드는 여전히 `analogy`, C(REQ004 v4.1) `LessonInput`은 여전히 `analogy_text`. B가 이번 개정에서 다른 필드는 다 손봤는데 이 항목만 그대로 남음. 08-03 조치표에서 "B가 필드명 확정 → C가 맞춤"으로 담당까지 정해뒀던 항목이라 가장 눈에 띄는 미조치 건.

### 2-2. [미해결] README.md가 REQ005/006 분리를 반영하지 못함

README 158~164행 담당 역할표는 여전히 D 한 줄에 "검증, 오케스트레이션, 인프라"를 묶고 `lib/`·배포 전반까지 D 소유로 기재, E 행이 없음. REQ005(D=검증만)·REQ006(E=인프라) 분리 이후에도 변경 없음.

### 2-3. [미해결, 신규 확인] B 문서 포맷이 여전히 팀 공통 템플릿과 다름

B v2.0에 개정 이력(0장)은 추가됐지만, A1/A2/C/D/E가 공통으로 갖는 "1. 프로젝트 개요" 표(요구사항 ID·담당자·작성일·문서 버전)와 "5. 승인" 섹션이 B에는 없음. "역할" 절이 그 자리를 대신하고 있어 다른 문서와 나란히 비교하기 어려움.

## 3. 신규 발견 이슈 (이번 재검토에서 처음 확인)

### 3-1. E(REQ006) 문서 본문이 D를 여전히 "REQ-003"으로 지칭

D는 v1.3에서 "요구사항 ID: REQ-005"로 자기 표기를 정정했고 실제로 E 문서의 표 값(`요구사항 ID: REQ-006`)도 맞다. 그런데 E 문서 **본문 두 곳**이 아직도 옛 번호를 쓴다:
- 1장 서두: "검증·오케스트레이션 로직은 **REQ-003(D)** 문서에서 별도로 다룬다"
- 핵심 설계 원칙: "판단 로직(...)은 **D(REQ-003)**가 소유한다"

REQ-003은 현재 B(매핑)의 번호라 D를 가리키는 REQ-003 표기가 B와 정면으로 겹친다. E 문서만 놓친 것으로 보이며, D 본문(및 표)은 이미 REQ-005로 일관되게 정정되어 있음.

### 3-2. A2·C 문서의 "담당 파일" 경로가 실제 코드와 어긋남

실제 레포(`find app/agents`) 기준 모든 에이전트가 `app/` 하위 패키지 폴더(`__init__.py`/`logic.py`/`prompts.py`/`schema.py`) 구조로 통일되어 있음. 그런데:
- A2(REQ-002) 담당 파일: `scripts/ingest_curriculum.py`, `agents/curriculum_search.py` → 실제는 `app/scripts/ingest_curriculum.py`, `app/agents/curriculum_search/`(4개 파일 패키지)
- C(REQ004) 담당 파일: `agents/lesson_generate.py` → 실제는 `app/agents/lesson_generate/`(4개 파일 패키지)

A1·D·E도 `app/` 접두어 누락이 문서 안에서도 표와 본문이 서로 다르게 쓰여 있지만(표는 `app/` 포함, 본문 서술은 생략), 이건 표기 누락 수준. A2·C는 **경로 자체가 실제 구조(패키지 vs 단일 파일)와 다르다**는 점에서 더 심각함 — 이번에 B가 REQ003을 실제 코드에 맞춰 고친 것과 같은 조치가 A2·C에도 필요.

### 3-3. `lib/types.py`의 `Subject`가 A2 문서와 어긋남

A2(REQ-002) v3.0은 "`lib/types.py` 실제 구현과 동기화하며 미구현 SOCIAL 값 제거"라고 명시하고 `Subject`를 `MATH`, `SCIENCE` 2개로 문서화했다. 그런데 실제 `app/lib/types.py`의 `Subject` enum은 `MATH`, `SCIENCE`, **`DOMESTIC_SCIENCE`** 3개 값을 갖고 있다(`app/data/raw/`에 실과 관련 PDF도 이미 존재). A2 문서가 "코드와 동기화했다"고 명시적으로 선언한 부분이라 이 차이가 특히 눈에 띔 — 실과(DOMESTIC_SCIENCE) 확장이 실제로 진행 중이라면 A2·A1(과목 힌트) 문서에 반영 필요.

### 3-4. B-07(재매핑 요청, `excluded_chunk_ids`) 처리 흐름이 D 문서에 없음

B(REQ003) B-07은 "D의 재매핑 요청(`excluded_chunk_ids`) 처리"를 필수 요구사항으로 명시하고, B 문서 2장은 `excluded_chunk_ids`를 "D(PipelineContext)" 입력 항목으로 받는다고 되어 있다. 하지만:
- D(REQ005)의 `PipelineContext`(VALID-000-2) 정의에는 `target_grade`, `subject_hint`만 있고 `excluded_chunk_ids` 필드가 없음.
- D의 ORCH-001/ORCH-002 어디에도 "B를 재호출한다"거나 "confidence가 낮으면 재매핑을 요청한다"는 흐름이 서술되어 있지 않음(D는 검증 실패 시 **C**를 재호출하는 루프만 정의).

즉 B가 자체 산출하는 `confidence < 0.50 → 재매핑 권고` 플래그를 누가, 언제, `excluded_chunk_ids`를 어떤 객체에 담아 B에 재전달하는지가 어느 문서에도 없음. B v2.0이 이 필드를 "D(PipelineContext)"로 뭉뚱그려 표기한 것도 이 미정 상태를 그대로 반영한 결과로 보임. D가 재매핑 트리거 조건과 전달 경로를 ORCH 문서에 명문화해야 B-07이 실제로 동작 가능.
